# 数据源与造数

> 本文是第一批文档的最后一份。产出物是：MySQL 建表 DDL、埋点 schema、四个生成器的接口、异常注入规则。
> **原则：不用公开数据集。** 天池那类 CSV 是死的——没有 UPDATE、没有迟到、没有脏数据，练不了维表变更、状态流转和对账。

**当前状态：四个生成器全部落地（2026-11-25）。** `trade` 库、5 个 topic、`gen_master.py`、`gen_history.py`、`gen_traffic.py`、`gen_realtime.py` 均已跑通并有实测数据；Spark、DS 侧仍未写。本文的参数是接口约定，已实现部分与实测结果一致（见第六节）。

## 一、数据源总览

```

│ MySQL  trade 库 │─────────────────────>│ Flink CDC J1 │──┐

└─────────────────┘                              └─────────────────┘
```

| 源 | 载体 | 内容 | 变更形态 |
|---|---|---|---|
| 业务库 | MySQL `trade` | 7 张表（4 事实 + 3 维表） | INSERT / UPDATE / 逻辑删除 |

| 埋点 | Kafka `ods_traffic` | 浏览、加购、下单点击 | 只追加，含重复与乱序 |

## 二、MySQL 表设计

### 2.1 建库

```sql
CREATE DATABASE IF NOT EXISTS trade
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;
```

时间统一 `DATETIME(3)`，保留毫秒——秒级精度在压测时区分不出事件先后。

### 2.2 维表（3 张）

```sql

CREATE TABLE user_info (
```

### 2.3 事实表（4 张）

```sql
CREATE TABLE order_info (
  order_id     BIGINT        NOT NULL COMMENT '订单ID',
  user_id      BIGINT        NOT NULL COMMENT '用户ID',
  shop_id      BIGINT        NOT NULL COMMENT '店铺ID',
  order_amount DECIMAL(12,2) NOT NULL COMMENT '下单金额',
  item_cnt     INT           NOT NULL COMMENT '商品件数',
  order_status SMALLINT      NOT NULL COMMENT '100待支付 200已支付 300已发货 400已签收 500已完成 600已取消',
  is_deleted   TINYINT       NOT NULL DEFAULT 0 COMMENT '逻辑删除',
  create_time  DATETIME(3)   NOT NULL COMMENT '下单时间',
  update_time  DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (order_id),
  KEY idx_update_time (update_time),
  KEY idx_create_time (create_time)
) ENGINE=InnoDB COMMENT='订单主表';

CREATE TABLE order_detail (
  detail_id  BIGINT        NOT NULL AUTO_INCREMENT,
  order_id   BIGINT        NOT NULL COMMENT '订单ID',
  product_id BIGINT        NOT NULL COMMENT '商品ID',
  num        INT           NOT NULL COMMENT '数量',
  price      DECIMAL(10,2) NOT NULL COMMENT '成交单价',
  amount     DECIMAL(12,2) NOT NULL COMMENT '小计 = num * price',
  create_time DATETIME(3)  NOT NULL,
  PRIMARY KEY (detail_id),

  KEY idx_create_time (create_time)
) ENGINE=InnoDB COMMENT='订单明细表';

CREATE TABLE payment_info (
  pay_id      BIGINT        NOT NULL COMMENT '支付流水号',
  order_id    BIGINT        NOT NULL COMMENT '订单ID',
  pay_amount  DECIMAL(12,2) NOT NULL COMMENT '支付金额',
  pay_channel VARCHAR(16)   NOT NULL COMMENT 'alipay/wechat/card',
  pay_status  TINYINT       NOT NULL COMMENT '1成功 2失败 3退款中',
  pay_time    DATETIME(3)   NOT NULL COMMENT '支付时间',
  update_time DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (pay_id),
  KEY idx_order_id (order_id),
  KEY idx_update_time (update_time)
) ENGINE=InnoDB COMMENT='支付流水表';

CREATE TABLE refund_info (
  refund_id     BIGINT        NOT NULL COMMENT '退款单号',
  order_id      BIGINT        NOT NULL COMMENT '订单ID',
  refund_amount DECIMAL(12,2) NOT NULL COMMENT '退款金额',
  refund_status TINYINT       NOT NULL COMMENT '0申请 1成功 2处理中 3拒绝',
  refund_reason VARCHAR(64)   NOT NULL COMMENT '退款原因',
  refund_time   DATETIME(3)   NOT NULL COMMENT '退款时间',
  update_time   DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (refund_id),
  KEY idx_order_id (order_id),
  KEY idx_update_time (update_time)
) ENGINE=InnoDB COMMENT='退款流水表';
```

### 2.4 DDL 里的三个刻意设计

| 设计 | 原因 |
|---|---|
| 每张表都有 `idx_update_time` | 离线 T+1 按 `update_time` 增量抽取，没有索引会全表扫 |
| `is_deleted` 逻辑删除 | 物理删除后实时侧无法解释"订单消失"，对账会少单 |
| 明细表存 `price` 快照 | 商品调价后，历史订单金额不能跟着变；这是维度快照语义的落点 |
| 退款有独立状态机 | `0 申请 → 2 处理中 → 1 成功 / 3 拒绝`，不能复用订单状态；生成器只造 `2→1` 与 `2→3` 两条路径，不造长期挂起 |

### 2.5 离线 T+1 的取数方式

**走 Spark JDBC 直读，按"事件日整片"抽取，不按 `update_time` 增量。** 实现在 `spark/offline_t1.py`，启动脚本 `scripts/run_offline_t1.sh`：

| 表 | 抽取条件 | 落 Hive |
|---|---|---|
| `order_info` | `create_time >= 当天 00:00 AND < 次日 00:00` | `ods.order_info`，`dt` = 当天 |
| `order_detail` | 同上（明细 `create_time` 与订单同刻） | `ods.order_detail` |
| `payment_info` | `pay_time` 当天，JOIN `order_info` 补 `user_id` / `shop_id` / `order_create_time` / `is_deleted` | `dwd.dwd_payment_detail`，`dt` = 支付日 |
| `refund_info` | `refund_time` 当天，同样 JOIN 订单 | `dwd.dwd_refund_detail`，`dt` = 退款日 |
| `shop_info` / `user_info` / `product_info` | 无条件全量 | `ods.*`，无分区，每次覆盖 |

参数：`--dt`（默认昨天）、`--host`（127.0.0.1）、`--port`（3306）、`--user`（root）、`--password`（默认读 `MYSQL_PASSWORD`，口令不落盘）、`--db`（trade）。每个 `dt` 分区都是 `INSERT OVERWRITE`，重复跑结果不变；补历史就是逐天传 `--dt`。

**为什么不用 2.4 里设计的 `update_time` 增量：** T+1 对账要的是"某一天全天的权威快照"，而增量抽取会把跨天变更混进来（昨天下的单今天支付），还得额外维护水位和去重。按事件日整片重算更简单、可重跑，代价是每天扫一遍当天范围——有 `idx_create_time` / 订单主键在，30 万单量级可接受。这条偏差记在 [08](./08-问题索引.md) D29。

**历史退款没有被自动补齐：** 退款按 `refund_time` 分区，10-25 ~ 11-24 的退款只在对应日期跑批时才会被抽到，而这些日期从未跑过。所以对历史日期补跑只会得到"当天发生的退款"，缺少"当天之前下单、当天之后退款"的部分。对账限制见 [06](./06-数据质量与对账.md) 6.5。

## 三、埋点 Schema

| 字段 | 类型 | 说明 |
|---|---|---|
| `event_id` | string | 事件唯一 ID，去重依据 |
| `user_id` | long | 与 MySQL 同一 ID 池 |
| `product_id` | long | 可为空（首页浏览无商品） |
| `event_type` | string | `page_view` / `add_cart` / `order_submit` |
| `event_time` | long | epoch 毫秒，**事件发生时间** |
| `session_id` | string | 会话 ID，30 分钟无操作切新会话 |

```json
{"event_id":"e-20261124-000001","user_id":10023,"product_id":5001,
 "event_type":"add_cart","event_time":1795525057808,"session_id":"s-8f3a2c"}
```

**`event_time` 与写入时间的分离是刻意的**：迟到数据要求"事件时间早、但很晚才到"，两者必须是两个独立字段。

## 四、生成器设计

代码放 `generator/`，全部 Python，依赖 `pymysql` + `kafka-python`。四个脚本，职责单一。

| 脚本 | 作用 | 运行方式 | 关键参数 |
|---|---|---|---|
| `gen_master.py` | 生成维表主数据 + ID 池 | 一次性 | `--users 100000 --products 50000 --shops 2000` |
| `gen_history.py` | 生成 30 天历史 | 一次性 | `--days 30 --orders-per-day 30000 --refund-rate 0.036` |
| `gen_realtime.py` | 实时交易状态机 | 常驻 | `--orders-per-min 20 --speed 10 --late-rate 0.01 --disorder-rate 0.005` |
| `gen_traffic.py` | 埋点流 | 常驻 | `--qps 200 --dup-rate 0.05 --late-rate 0.01 --bad-type-rate 0.001 --bad-time-rate 0.001 [--duration 秒]` |

`--qps 200` 是**日常默认值**，用于持续观察延迟与质量规则；压测时传 `--qps 2000`（见第六节）。两个数字是同一脚本的不同参数，不冲突。

### 4.1 顺序与依赖

```
gen_master.py ──> id_pool.json ──> gen_history.py ──> gen_realtime.py
                                            └──────> gen_traffic.py
```

`gen_master.py` 产出 `id_pool.json`（用户/商品/店铺 ID 范围），后三个脚本读取它。**这是三端 ID 打通的关键**：埋点里的 `user_id` 必须命中 MySQL 的用户，否则漏斗对不上。

### 4.2 实时交易状态机

`gen_realtime.py` 的核心不是"插一条订单"，而是**按时间推进状态**（下表是业务时间；`--speed 10` 时真实等待 = 业务秒 / 10）：

| 步骤 | 业务延迟 | 动作 |
|---|---|---|
| 1 | t=0 | INSERT `order_info`（100 待支付）+ 1~5 行 `order_detail` |
| 2 | +30~120 秒 | INSERT `payment_info`，UPDATE 订单为 200 |
| 3 | +5~15 分钟 | UPDATE 订单为 300 |
| 4 | +30~60 分钟 | UPDATE 订单为 400 |
| 5 | +60 分钟 | UPDATE 订单为 500 |
| 旁支 | 支付后 3% | INSERT `refund_info`（先 2 处理中），60 秒~30 分钟后改成 1 成功（88%）/ 3 拒绝（12%） |

`--speed` 是时间加速倍率，默认 10 倍，方便演示时几分钟看到完整生命周期。**`--speed` 只压缩等待间隔，写库时间戳一律用真实时间**：如果把 `create_time` 写成"业务时间"（未来），J3 的分钟窗口会被未来水印提前推高（与 08 E27 同源）。每一步都是一次真实的 INSERT/UPDATE，J1 的 CDC 才有事件可抓。

**已落地（2026-11-25）**：`generator/gen_realtime.py`，启动脚本 `scripts/run_gen_realtime.sh`（`MYSQL_PASSWORD` 从环境变量或 `--password` 传入，不落盘）。实现要点：

| 点 | 做法 |
|---|---|
| 调度 | 单线程时间堆，每步到点执行一条真实 SQL；`autocommit=True`，CDC 立即可见 |
| 订单号 | `启动毫秒 × 1000 + 序号`（约 1.79e15），不与历史单（1~90 万）和冒烟单（9 亿段）冲突 |
| 明细 | 1~5 个商品、件数 1~3、价格在商品价 ±5% 浮动；`order_amount` = 明细金额之和 |
| 参数 | `--speed`(10)、`--orders-per-min`(20)、`--duration`(0 常驻)、`--late-rate`(0.01)、`--disorder-rate`(0.005)、`--bad-amount-rate`(0.002)、`--dim-miss-rate`(0.02)、`--refund-rate`(0.03)、`--seed` |
| 信号 | Ctrl+C / SIGTERM 优雅退出，打印订单/支付/退款/异常/错误计数 |
| 实测 | `--duration 40 --speed 120 --orders-per-min 1` + 各项异常调到 10%~30%：80 单 / 158 明细 / 76 支付 / 19 退款 / 迟到 10 / 乱序 7 / 金额异常 6 / 维表缺失 7 / 错误 0；DWD 76 笔支付全部落库、`pay_time` 逐笔一致，12 笔成功退款金额/时间一致，状态分布与 MySQL 完全相同 |

### 4.3 埋点流

`gen_traffic.py` 按 `--qps` 匀速写 Kafka，key 用 `user_id`（保证同一用户的事件有序）。事件类型比例：浏览 90%、加购 8%、下单点击 2%——和交易数据能对上（下单点击数 ≈ 订单数的 1.2 倍）。

**已落地（2026-11-25）**：`generator/gen_traffic.py`，启动脚本 `scripts/run_gen_traffic.sh`（WSL 内前台运行，Ctrl+C 优雅退出并打印汇总；`--duration` 到点自动退出）。实现要点：

| 点 | 做法 |
|---|---|
| ID 来源 | 读 `generator/id_pool.json`，`user_id` / `product_id` 必落在 MySQL 已有 ID 范围内，漏斗能对上 |
| 事件 ID | `e-<启动时间>-<9 位序号>`，一次运行内不重复，重启也不会撞 |
| 商品 | 浏览事件 20% 不带 `product_id`（首页场景），加购/下单点击必带 |
| 会话 | 同一用户 30 分钟内有事件就复用 `session_id`，超时切新会话（实测 10 分钟内复用、超 30 分钟切换） |
| 节奏 | 按绝对时间片推进，卡顿后不补发旧事件，避免瞬时洪峰 |
| 指标 | 每 10 秒打印逻辑事件数、实际消息数、重复/迟到/非法类型/越界时间计数，退出时给汇总 |

除第五节列的 5% 重复外，埋点链路还按小比例造两类**质量问题靶子**，供 J4 的 Q04 / Q05 规则命中（与 `06` 第三节对应）：

| 靶子 | 参数 | 默认 | 实现 |
|---|---|---|---|
| 非法枚举 | `--bad-type-rate` | 0.1% | `event_type` 写 `click_buy` / `cart_add` / `buy_now` / `unknown` |
| 时间越界 | `--bad-time-rate` | 0.1% | 只写早于当前 31~45 天（原来一半写未来 5~60 分钟，会把 Flink 水印推飞、分钟窗口停摆，见 08 E38） |

迟到事件（`--late-rate`，1%）把 `event_time` 前移 5~30 分钟，但仍在 30 天有效范围内，属于合法数据，J4 不拦截，只影响实时性。异常注入互斥：一条事件只命中一种，重复只对合法事件做，便于把脏数据计数和注入计数一一对上。

## 五、五类异常注入

这五类是 **`06-数据质量与对账` 里规则的靶子**，必须真的造出来，不能只在文档里写。

| # | 异常 | 注入位置 | 比例 | 实现方式 |
|---|---|---|---|---|
| 1 | 埋点重复 | `gen_traffic.py` | 5% | 同一 `event_id` 重复发送 2 次 |
| 2 | 支付回调迟到 | `gen_realtime.py` | 1% | `pay_time` 写"应支付时刻"，但 `payment_info` 行晚 5~15 分钟业务时间才落库（消息晚到，事件时间不变） |
| 3 | 状态乱序 | `gen_realtime.py` | 0.5% | 先写 200（已支付），2 秒后补一条 `update_time = create_time - 60s` 的 100，再 2 秒后恢复 200 |
| 4 | 金额异常 | 两个脚本 | 0.2% | `order_amount` 写 0 或负数 |
| 5 | 维表缺失 | `gen_master.py` + 订单 | 少量 | 商品置 `status=0` 后仍产生订单 |

对应的识别方式（详细规则在 06）：

| # | 识别点 |
|---|---|
| 1 | DWD 按 `event_id` 去重，统计去重量 |
| 2 | 水位线 + 迟到计数，超出窗口落离线补数 |
| 3 | 按 `update_time` 幂等覆盖，乱序事件不生效 |
| 4 | 质量规则 `order_amount > 0` |
| 5 | Lookup Join 未命中 → 兜底"未知商品"维 |

## 六、量级与压测配置

| 未来时间戳 | 0 行（`update_time` / `refund_time` 均截断到当前时刻之前） |
| 埋点生成器（200 QPS） | 连续 269.8 秒：53,957 条逻辑事件 / 56,649 条消息；重复 2,692（4.99%）、迟到 553（1.02%）、非法类型 56（0.10%）、越界时间 67（0.12%），发送错误 0 |
| 实时交易生成器（短测） | `--duration 40 --speed 120 --orders-per-min 1`：80 单 / 158 明细 / 76 支付 / 19 退款（12 成功）；迟到 10 / 乱序 7 / 金额异常 6 / 维表缺失 7，错误 0；DWD 的支付、退款字段与 MySQL 逐笔一致（详见 08 E31） |
| 压测（埋点） | 200 QPS 已实测；2000 QPS × 30 分钟未跑 |

压测只压埋点链路，不压交易链路——交易量受 MySQL 单机写入限制，硬压会先打挂数据库，测不出 Flink 的问题。

## 七、开工前必须做的环境准备

### 7.1 MySQL 开启 binlog

```ini
# /etc/mysql/mysql.conf.d/mysqld.cnf
[mysqld]
server-id                = 1
log_bin                  = mysql-bin
binlog_format            = ROW
binlog_row_image         = FULL
binlog_expire_logs_seconds = 604800
```

校验：

```sql
SHOW VARIABLES WHERE Variable_name IN ('log_bin','binlog_format','binlog_row_image');
-- 期望：ON / ROW / FULL
```

`binlog_row_image=FULL` 是必须的：只记 `MINIMAL` 时 UPDATE 事件不带完整旧值，CDC 无法构造完整变更。

### 7.2 创建 CDC 账号

本地口令统一（与业务库同一口令），仓库里只写占位符，执行前替换：

```sql
CREATE USER 'cdc'@'%' IDENTIFIED BY '__CDC_PASSWORD__';
GRANT SELECT, RELOAD, SHOW DATABASES, REPLICATION SLAVE, REPLICATION CLIENT
  ON *.* TO 'cdc'@'%';
FLUSH PRIVILEGES;
```

Flink CDC 需要 `REPLICATION SLAVE` 和 `REPLICATION CLIENT` 读 binlog，`RELOAD` 用于加锁做全量快照一致性读。

### 7.3 建 Kafka topic

```bash
K=/home/hzh/apps/kafka
for t in "ods_order 3" "ods_order_detail 3" "ods_payment 3" "ods_refund 3" "ods_traffic 6"; do
  set -- $t
  $K/bin/kafka-topics.sh --bootstrap-server 127.0.0.1:9092 \
    --create --topic $1 --partitions $2 --replication-factor 1
done
$K/bin/kafka-topics.sh --bootstrap-server 127.0.0.1:9092 --list
```

分区数不要事后改：改分区会打乱 `key` 到分区的映射，同一 `order_id` 的变更可能落到不同分区，顺序保证失效。

### 7.4 首次启动顺序

| 顺序 | 动作 | 原因 |
|---|---|---|
| 1 | 建库建表、开 binlog、建 CDC 账号 | CDC 要能读到全量快照 |
| 2 | `gen_master.py` → `gen_history.py` | 先有维表和历史单，否则离线 T+1 没有 T-1 可对 |
| 3 | 建 5 个 topic；手动跑一次维表快照（`dim_snapshot`） | 否则 J2 首日的 Lookup Join 全落到"未知商品" |
| 4 | 起 J1（CDC → Kafka），确认 4 个交易 topic 有数据（`ods_traffic` 由埋点生成器写） | 先起 J1 再写库，变更才不会被漏 |
| 5 | 起 J2~J5，再起 `gen_realtime.py` / `gen_traffic.py`；ADS 用 `bash scripts/run_j6.sh --loop 60` 或交 DS 触发 | 先有消费端，避免开局堆积；J6 是 Doris SQL 定时批，不是常驻 Flink 作业（04 4.2 / 08 D26） |

**第 2 步必须在 J1 之前。** 90 万历史单只进 MySQL、不进 Kafka；如果先起 J1 再跑 `gen_history.py`，这 90 万条 INSERT 会被 binlog 全量捕获并灌进 `ods_order`，等于开局先给自己造一次积压。历史数据用批量 `INSERT` 而非逐条造数，另一个原因也是避开这条链路。

## 九、已知取舍

1. **历史数据是批量 INSERT**，不经过 Kafka——它不是"实时事件"，只用于给离线链路和维表提供存量。实时链路只处理生成器启动之后的增量。
2. **退款只走一条路径**（全额退款），不做部分退款与多次退款，避免退款表爆炸；口径上仍按"退款金额"统计，不影响指标正确性。
3. **不做商品改价的历史版本**，`product_info.price` 只保留当前值；订单里存成交价快照，所以历史金额不受影响。真正需要价格版本时应改用拉链表。
