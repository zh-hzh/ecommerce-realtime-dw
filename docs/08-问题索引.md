### E01 细节：Doris 卡 UNKNOWN

宿主 IP 是 DHCP，换网就变一次。Doris FE 的元数据里登记了 BE 的旧地址，BE 重启后用自己的新地址注册，FE 认不上，`SHOW BACKENDS` 里 `isAlive=false`，建表能过但写入全失败。

处理是把整个集群锁在回环地址上：FE `priority_networks = 127.0.0.1/32`，BE 同样，所有客户端也只连 `127.0.0.1`。代价是不能从宿主以外访问，但这个项目所有消费端都在同一台 WSL 里，没有影响。

### E03 细节：ZK → KRaft

原来走 ZooKeeper：多一个进程、多一套选举、Kafka 3.x 官方已宣布逐步移除 ZK 模式。切换的关键是**数据和元数据不能复用**：

1. 停 Kafka、停 ZK，`systemctl disable zookeeper`
2. 新配置 `process.roles=broker,controller`、`controller.quorum.voters=1@127.0.0.1:9093`、`log.dirs=data/kraft-logs`
3. `kafka-storage.sh format -t <cluster.id>` 重新格式化
4. 旧数据目录改名 `kafka-logs.zk.bak` 留档（**ZK 模式的数据 KRaft 读不了**，只能重来）
5. 验证：建 topic、生产、消费

踩坑点：`cluster.id` 必须和 format 时一致，否则启动报 `InconsistentClusterIdException`。

### E13 细节：WSL 重启自检（2026-11-24 22:50）

**原状：** 宿主 WLAN 是 DHCP，WSL 的 `eth0/eth3` 地址随宿主变化。E01 把 FE/BE 锁在回环地址后，Doris 不再依赖宿主 IP，但"整机重启之后能不能自己回来"一直没有实测过，只是推断。

### E15 / E16 细节：J2 首版建表踩的两个 Doris 限制（2026-11-25）

**原状：** 按 03 的设计直接建 `dw.dwd_trade_order_detail`：`UNIQUE KEY(order_id)` + `PARTITION BY RANGE(dt)`，不带副本数。两次报错，原文分别是 `Merge-on-Write table's partition column must be KEY column` 和 `replication num should be less than the number of available backends`。

**原因：** 一是 Doris 的 MoW Unique 表要求分区列必须是 key 列，`dt` 不在 key 里就直接被拒；二是副本数默认 3，而本机只有 1 个 BE（单副本环境），不改必然失败。

**改成什么：** key 改成 `(order_id, dt)`，`dt` 由 `create_time` 取日期，订单不下改 `create_time`，所以"一单一行"的语义没变；副本数显式写 1。同一张表当时还用 `function_column.sequence_col = update_time` 实现 03 5.1 的"按 `update_time` 幂等覆盖"——乱序或重放写入时，Doris 只保留 `update_time` 更大的那版（该属性后被 E31 撤掉）。

**后续（2026-11-25）：** J2 第三版把 key 改回 `order_id` 并取消分区（部分列更新需要 key 只有订单 ID，见 D20），这条"分区列必须是 key 列"的约束随之不再适用；E15 留作记录。

**验收：** 建表成功，`information_schema.partitions` 里 94 个分区（动态分区 -90 天 + 未来 3 天）；`scripts/smoke_j2.sh` 插入 → 更新 → 软删三步都能在 Doris 查到，各约 10~12 秒（受 10s checkpoint + 2PC 提交约束），清理测试行后作业仍 RUNNING、`exceptions` 为空。

### E18 细节：Stream Load 的认证与 307 重定向（2026-11-25）

**原状：** 第一次用 `curl -X PUT http://127.0.0.1:8030/api/dw/dim_shop/_stream_load -T xxx.tsv` 灌维表，返回 `{"msg":"Unauthorized","code":401,"data":"Need auth information."}`。加上 `-u 'root:'` 后返回体变空，脚本按失败处理。

**原因：** 两段独立的坑。① FE 的 `/_stream_load` 要求 Basic 认证，不带 `-u` 直接 401；② 带上认证后 FE 返回 `307 Temporary Redirect` 把请求指到 BE 8040，curl 默认**不把 `Authorization` 头带到重定向目标**（跨端口视为不同 origin），于是 BE 侧报 `[NOT_AUTHORIZED]no valid Basic authorization`；因为没加 `-L`，脚本拿到的还是空响应体，看起来像"没返回"。

**改成什么：** `curl -sS -L --location-trusted -X PUT ... -u 'root:'`——`--location-trusted` 让认证头跟随重定向，`-L` 让响应体是 BE 的真实 JSON。另外返回值是带缩进的 JSON，判断成功要用 `grep -qE '"Status"[[:space:]]*:[[:space:]]*"Success"'`，不能写死 `"Status":"Success"`。实测 2000 行 156 KB 一次装完，41 ms。

### E19 细节：Doris sink 的 label 前缀不能跨作业复用（2026-11-25）

**原状：** J2 第二版（加 Lookup Join）提交后 job 一直在 `RESTARTING`，`/jobs/:id/exceptions` 的根因是 `Load status is Label Already Exists and load job finished, change you label prefix or restore from latest savepoint!`。作业重启前已经写进 Doris 一条新单（插入可见），但后续 checkpoint 提交全部失败。

**原因：** Doris Stream Load 的 label 是**全局唯一**的，Doris sink 用 `sink.label-prefix + subtask + checkpointId` 拼 label；新版作业沿用了首版的 `j2_dwd_trade`，而首版已经提交过相同组合的 label，Doris 认定重复。

**改成什么：** 每次重新提交作业都换一个 label 前缀（本次 `j2_dwd_trade_v2`），并在 SQL 头注释里写明"重提必换"。同一次作业的正常重启/从 checkpoint 恢复不受影响，因为 label 跟着 checkpoint 恢复走。

### E20 细节：部分列更新的三个前提（2026-11-25）

**原状：** 打算让订单 / 支付 / 退款三条流各写 DWD 的一部分列，靠 Doris 部分列更新合并。先建临时表 `dw.t_partial` 用 curl 直接灌 JSON 验证，第一版请求只带 `format:json` + `read_json_by_line:true` + `partial_columns:true`，结果后续行把前一行已有的 `dt`、`user_id` 冲成了 NULL。

**原因：** 三个点都不满足。① `format:json` + 数组会报 `JSON data is array-object, strip_outer_array must be TRUE`，Flink 用的是逐行对象，验证脚本也得逐行写；② 不带 `columns` 头时，Doris 按"整行"处理，JSON 里缺的 key 视为 NULL 并写入，所以第二行把 `dt`/`user_id` 置空了；③ 带上 `columns` 头但不带 `Expect:100-continue` 时，直接返回 `There is no 100-continue header` 拒绝。

**改成什么：** `columns` 头**只列本次要写的列**（例如支付分支 `order_id,pay_id,pay_amount,pay_status,pay_time,update_time`），没列进去的列 Doris 不动；JSON 的 key 和 `columns` 保持一致；请求必须带 `Expect:100-continue`。实测：先写全列，再只用 `columns:order_id,pay_amount,update_time` 写第二次，`dt`/`user_id` 原样保留、`pay_amount` 更新。Flink 侧对应做法是每个 sink 的 DDL 只声明自己那几列，并配 `sink.properties.partial_columns=true` + `sink.properties.columns=<同样几列>`。（当时还观察到"`update_time` 更小的写入被 sequence 忽略"，正是这条属性后来造成 E31 的丢数，已撤掉。）

### E31 细节：`sequence_col` 让跨流的部分列更新整行失效（2026-11-25）

**原状：** `gen_realtime.py` 短测生成 150 单 / 149 笔支付，MySQL 与 DWD 的 `order_status` 分布完全一致（1/28/37/53/31），但 DWD 只有 36 行带 `pay_id/pay_amount/pay_time`。把两侧数据导出来逐单比对：113 个缺失行**全部**满足 `DWD.update_time >= payment_info.update_time`，没有一个反例。

**原因：** `dw.dwd_trade_order_detail` 带了 `function_column.sequence_col = update_time`。Doris 的 sequence 是**表级**属性，不是"每组列各自比较"——部分列更新同样参与 `update_time` 比大小，sequence 更旧时整行更新被丢弃。J2 的三个 sink 在同一个 checkpoint 里各自做 Stream Load 2PC，提交先后没有保证：订单流的发货/签收/完成更新只要先提交，支付分支随后提交的部分列更新就会被判"更旧"整行扔掉。造数用 `--speed 120` 把整条生命周期压缩到几十秒，竞争被放大，所以在实测里丢 113/149。临时表对照实验：同一行先按 `update_time=10:00:00` 整行写入，再用 `10:00:30` 部分更新（生效），再用 `10:00:10` 部分更新——带 sequence 的表 `b` 仍为旧值、整条被忽略；去掉 sequence 的表正常覆盖成新值。

**改成什么：** 建表去掉 `function_column.sequence_col`，`sql/02_init_doris.sql` 与 `flink/sql/j2_dwd_trade.sql` 头注释同步改写。理由：三组列互不重叠，同一条流由同一个 sink 按 checkpoint 顺序提交，`Unique Key + MoW` 的"后写覆盖"就能合并出一行，不需要跨流比较先后。线上表用"建新表 → 搬 155 行 → 换名 → 删旧表"重建（Doris 不支持把 `sequence_col` 置空，`ALTER ... SET` 报 `Unknown table property`）。验收：新跑 80 单 / 76 笔支付，DWD 76 笔全部落库、`pay_time` 逐笔一致（含 10 笔迟到支付），19 笔退款流水中 12 笔成功的金额/时间全部一致，状态分布与 MySQL 完全相同。

**副作用：** DWD 不再自动丢弃"更旧"的更新，状态乱序注入（Q10）会让 DWD 短暂倒退到 100、2 秒后被源端补正；[06](./06-数据质量与对账.md) 的 Q10 口径由"丢弃更新数"改为"倒退更新数"。

### E32 细节：Doris 的 VARCHAR 结果右补空格（2026-11-25）

**原状：** `spark/reconcile.py` 第一版把 Doris 的 5 个指标读成一个 dict，再用 `realtime["pay_cnt"]` 取数，直接走到 `Doris 没有返回指标：['pay_cnt', ...]` 退出。用 mysql 客户端同样 SQL 直查，5 行都在、值也对。

**原因：** Doris 走 MySQL 协议返回结果集时，`VARCHAR(32)` 列会按列宽右补空格，实际读到的 key 是 `'pay_cnt                        '`（长度 32）。Python 字符串比较区分尾部空格，字典取不到值；本地 mysql 客户端展示时会裁掉尾部空白，所以看不出来。

**改成什么：** 读回后统一 `r["metric"].strip()` 再建 dict，并在代码里留注释。这类"看起来有值但取不到"的问题只在跨协议读取文本列时出现，金额列（DECIMAL）不受影响。

**验证：** 修复后同一条 `UNION ALL` SQL 返回 5 个指标齐全，对账正常出结果。

### E33 细节：PySpark 3.5 在 Python 3.14 下序列化本地数据失败（2026-11-25）

**原状：** 对账结果 5 行原本打算用 `spark.createDataFrame(rows, schema)` 生成，运行报 `_pickle.PicklingError: Could not serialize object: RecursionError: Stack overflow (used 8156 kB)`，堆栈全在 cloudpickle 的 `_reconstruct` 里。

**原因：** 系统 Python 是 3.14，PySpark 3.5 的 cloudpickle 版本较旧，序列化 DataFrame 构造函数时递归深度超限。这与业务代码无关，是依赖组合的兼容问题。

**改成什么：** 不经过本地数据：把 5 行拼成 `SELECT ... UNION ALL SELECT ...` 的 SQL，由 Spark 自己生成 DataFrame 再 `append` 写 Doris。同时删掉不再使用的 `pyspark.sql.types` 导入。离线跑批（`offline_t1.py`）全程用 Spark SQL / JDBC，不碰 `createDataFrame`，所以没受影响。

**后续注意：** 本项目里任何"本地小数据转 DataFrame"的写法都要避开 `createDataFrame`，改用 `spark.sql("SELECT 1 AS x")` 一类方式。

### D09 细节：不写死凌晨定时

原设计是 cron：01:00 维表、02:00 离线、04:00 对账、05:00 巡检。问题很直接——**机器不在线，任务不会跑，也不会自己补**。DS 的补数本身要手动点。

改成一条手动工作流：

| 事项 | 做法 |
|---|---|
| 触发 | 开机后打开 DS 手动运行一次 |
| 参数 | 默认 `dt = T-1` |
| 断档 | 填 `start_dt` / `end_dt`，按日期逐个实例补跑 |
| 结论可信度 | 靠"取 T-1 分区 + 可重跑"保证，不靠跑得早 |

对账数值只取决于分区内容，和触发时刻无关；要守的是"跑完冻结、重跑以最新为准"。

## 五、第二轮评审（2026-11-24）

外部评审提了 7 条，按"原来是什么 → 为什么改 → 改成什么"记。结论先给：**A / B / D / E 成立且已改，C 描述过时，F 部分成立，G 成立且优先级最高。**

### R-A `order_detail` 数据流不完整（成立，最严重）

**原来：** 05 定义了 7 张 MySQL 表（含 `order_detail`），04 的 J1 只输出 3 个交易 topic（order / payment / refund），DWD 是订单粒度、没有商品字段；06 的 C02 又依赖 `order_detail`。

**为什么必须改：** 不只是一张表缺通路。实时侧的"分品类支付金额"和"TOP N 商品"都基于明细，离线有、实时没有，等于 02 里两个指标只有一半能实现；ADS 的 `ads_topn_product` 更是没有上游。

**改成什么：**

| 改动 | 位置 |
|---|---|
| 新增 topic `ods_order_detail`（3 分区，key `order_id`，只追加） | 04 4.1 |
| J1 输出 5 个 topic；J2 输入加 detail；J3 消费 detail × dim 算商品粒度 | 04 4.2 |
| 新增 `dws_trade_product_1h`（`stat_hour + product_id`），业务表 16 → 17 | 03 二节 |
| 离线侧明确"7 张表全量快照，含 detail"，与实时互不依赖 | 04 4.2 |
| 建 topic 脚本、启动顺序、验收数量同步 | 05 7.3 / 7.4 / 八 |

**留了个尾巴：** J3 仍是 3 并行度，`dws_trade_product_1h` 的行数（5 万商品 × 24 小时活跃组合）没压过，等实测再调。

### R-B C02 的执行方没写（成立）

**原来：** 06 给了一段 Hive SQL，末尾 `INSERT INTO dwd_dirty_record`，读起来像是在 Hive 里直接写 Doris。

**为什么：** Hive 没有跨库写能力，这段必须有桥梁，否则文档不可执行。

**改成什么：** 明确 `quality_check` 是 DS 的 Shell 节点，调 `spark-submit`；Spark 读 Hive、`filter` 出不符行，再用 Doris Spark Connector 或 JDBC 写回。写入量只有脏数据行数，JDBC 足够。

### R-C 01 第五节格式不统一（描述过时，不改）

**原状核实：** 评审说"环境表后追加了四条独立段落"，但当前 01 已经有 `### 5.1 验证记录` 和一张五行表格（检查 / 命令 / 结果），不是散文。

**结论：** 不改。硬并入环境表的"状态"列会丢掉命令原文，验证记录的价值恰恰在命令能复跑。

### R-D 压测吞吐标注有歧义（成立）

**原来：** 一行写"埋点 2000 QPS 稳定 30 分钟"，括号注明"日常默认 200 QPS"。

**为什么：** 第一眼读到的是 2000，括号里的信息被吞掉，容易被理解成日常就在跑 2000。

**改成什么：** 拆两行——"日常吞吐 200 QPS"和"压测吞吐 2000 QPS × 30 分钟"，各自独立状态。

### R-E 状态写法不统一（成立）

**原来：** 01 写"设计阶段"，02/03/04 写"初稿"，05/06 写"设计完成（代码未写）"。

**为什么：** 同一批文档三个说法，读者无法判断完成度。

**改成什么：** 六份统一为"设计完成（代码未写）"；01 维护规则里定义枚举：`初稿 → 设计完成（代码未写）→ 已落地 → 已验收`。

### R-F 04 调度表与"手动触发"并存（部分成立）

**原来：** 4.3 先给一张 DS 任务表，后文说"不用 cron、改手动工作流"，没交代两者关系。

**为什么：** 容易被读成"推翻前面的表"。

**改成什么：** 表前补一句——四个节点是同一条工作流 `nightly_t1` 的四个串行步骤，DS 是编排器不是定时器；薄弱点 #7 同步改成"不配 cron，不是不用 DS"。

### R-G 六份文档零代码（成立，最高优先级）

**原状：** 约 5 万字设计，`generator/`、Flink SQL、Spark 作业、DS 工作流全部为空。

**判断：** 不反驳。文档能支撑"讲得清"，但回答不了"跑起来了吗"。评审给的建议顺序也和我的计划一致：`gen_master` → J1 → J2 简化版，先让一条数据从 MySQL 走到 Doris。

**改成什么：** 本轮之后停止扩写文档（07 只写操作命令，作为落地的执行手册，不再补设计）；下一步按最小链路推进，实测数字回填 01 第四节。
