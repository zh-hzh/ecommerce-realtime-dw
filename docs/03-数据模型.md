# 数据模型

> 输入是 [02-指标体系](./02-指标体系.md)。本文只回答一件事：**为了算出那些指标，表应该长什么样。**

## 一、分层职责与边界

| 层 | 职责 | 边界判定 | 是否可直接查询 |
|---|---|---|---|
| **ODS** | 原样保留源端变更 | 不做任何清洗、不去重、不关联 | 否（仅供排查） |
| **DIM** | 提供稳定的维度描述 | 只存"描述性字段"，不存度量 | 是 |
| **DWD** | 一行一个业务过程实体，完成清洗与打宽 | **只做明细，不做聚合** | 是 |
| **DWS** | 按维度 + 时间粒度做轻度汇总 | 只存可加指标（SUM/COUNT） | 是 |
| **ADS** | 面向看板的结果表 | 一个指标（或一组相关指标）一张表 | 是（看板只查这层） |

三条判定规则：

1. **能加总的进 DWS，需要去重的留在 DWD 或另做 bitmap。** UV 不可加，不能简单放进 SUM 型 DWS。
2. **维度字段在 DWD 就退化冗余，不在查询时 join。** 见 6.2。
3. **ADS 只做取数与排序，不做聚合。** 聚合前移到 DWS；唯一留下的计算是 TOP N 的排名（`rank_no`），因为它必须看全量才能排。否则看板查询会慢。

## 三、ODS 层

ODS 只做一件事：**把源端变更原样接住**，包括 UPDATE 和 DELETE。用 Doris `Duplicate Key` 模型，因为同一个 `order_id` 会有多条记录，必须全部保留。

### `ods_order`

| 字段 | 类型 | 说明 |
|---|---|---|
| `order_id` | BIGINT | 订单号 |
| `user_id` | BIGINT | 用户 |
| `shop_id` | BIGINT | 店铺 |
| `order_amount` | DECIMAL(12,2) | 下单金额 |
| `order_status` | INT | 状态机 |
| `create_time` | DATETIME | 下单时间（事件时间） |
| `update_time` | DATETIME | 源端更新时间 |
| `op_type` | VARCHAR(8) | `I` / `U` / `D`，来自 binlog |
| `dt` | DATE | 入库日期 |

`ods_payment`、`ods_refund` 结构同构，分别对应支付与退款；`ods_traffic` 为埋点 JSON 展开。

**为什么要保留 `op_type`：** DELETE 在业务库是硬删或软删，ODS 必须能看出这条是删除操作。DWD 侧据此做"逻辑删除标记"，否则订单消失了你无法解释。

## 四、DIM 层

### 4.1 SCD 策略：每日全量快照

三个维表都采用 **每日全量快照**（`dt` 分区，每天一份完整数据），而不是拉链表。

| 方案 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| **每日全量快照**（选它） | 每天全量写一份 `dt=xxx` 分区 | 简单、可回溯任意一天、回刷容易 | 空间放大 |
| 拉链表 | `start_date` / `end_date` / `is_current` | 省空间 | 更新逻辑复杂，查历史要带时间条件 |
| SCD1 覆盖 | 只留最新 | 最省 | 丢失历史，无法回溯 |

选全量快照的理由：维表数据量小（商品万级、用户十万级、店铺千级），空间不是问题；而**可回溯**对调试更有价值——"2026-11-20 那天的商品类目是什么"能直接查。

被问到"为什么不用拉链表"时的答法：数据量小、查询简单优先；拉链表适合维表大且变更频繁的场景，实现要点是 `start_date`/`end_date`/`is_current` 三段式，本项目了解但没选。

### 4.2 三张维表字段

| 表 | 字段 |
|---|---|
| `dim_product` | `product_id`, `product_name`, `category_id`, `category_name`, `brand`, `price`, `status`（Doris 落地另加 `update_time`、`snapshot_date`） |
| `dim_user` | `user_id`, `gender`, `age_range`, `city`, `register_time`, `user_level` |
| `dim_shop` | `shop_id`, `shop_name`, `shop_type`, `province`, `city`（Doris 落地另加 `create_time`、`snapshot_date`） |

## 五、DWD 层

### 5.1 `dwd_trade_order_detail`：累积快照事实表

这是整个模型的核心，也是最容易被追问的一张表。

**为什么是累积快照：** 一个订单的生命周期有多个里程碑（下单 → 支付 → 发货 → 签收 → 完成 → 退款），每个里程碑都会更新同一行。累积快照事实表的特征就是**一行一单、多个时间戳字段、随业务推进不断更新**。

| 分组 | 字段 | 说明 |
|---|---|---|
| 主键 | `order_id` | |
| 维度（退化） | `user_id`, `shop_id`, `province`, `city` | 从 `dim_shop` 冗余，避免查询 join |
| 度量 | `order_amount`, `item_cnt`, `pay_id`, `pay_amount`, `refund_amount` | |
| 里程碑 | `create_time`, `pay_time`, `ship_time`, `receive_time`, `finish_time`, `refund_time` | 未发生为 NULL |
| 状态 | `order_status`, `pay_status`, `refund_status`, `is_deleted` | |
| 控制 | `update_time`, `dt` | |

`pay_id` 是一单一支付场景下最近一次支付流水号，保留它是为了让"支付笔数按 `pay_id` 去重"这条口径（[02-指标体系](./02-指标体系.md) 第五节）能在 DWD 上直接算，不用回查支付流水表。

**三条设计约束：**

1. **同一行后写覆盖（不用 `sequence`）**：`Unique Key(order_id)` + MoW，三组列各写各的，同一 key 后提交的批次覆盖先提交的。**表上不能加 `function_column.sequence_col`**：sequence 是表级属性，三个 sink 在同一 checkpoint 内的提交顺序不保证，支付/退款的部分列更新一旦晚于订单状态更新提交，会因 `update_time` 更旧被整行丢弃（实测 149 笔支付丢 113 笔，见 [08](./08-问题索引.md) E31）。
2. **时间戳只前进不后退**：`pay_time` 已有值时不覆盖为 NULL，防止迟到消息把已支付订单改回未支付。落地做法见下面的"三流合并"。
3. **逻辑删除**：`op_type = D` 时不物理删，置 `is_deleted = 1`，否则对账会少单。

**落地方式：三流各写各的列（2026-11-25，J2 第三版）。** 里程碑事件分散在 `ods_order` / `ods_payment` / `ods_refund` 三条流，时间跨度可到 20 天，用 interval join 留不住这么长状态，而且订单流单独触发时拿不到支付/退款字段。改成：

| 分支 | 写入的列 | 来源 |
|---|---|---|
| 订单 | 订单字段 + `province` / `city` | `ods_order` + Lookup `dim_shop` |
| 支付 | `pay_id`、`pay_amount`、`pay_status`、`pay_time` | `ods_payment`（只取 `pay_status=1`） |
| 退款 | `refund_amount`、`refund_time`、`refund_status` | `ods_refund`（只取 `refund_status=1`） |

三组列互不重叠，Doris 用**部分列更新**（`partial_columns`）合并到同一行，谁先到都不冲掉对方；同一条流由同一个 sink 按 checkpoint 顺序提交，后写覆盖即正确结果。代价是 **key 只能是 `order_id`，`dt` 退化成普通列、不能做 RANGE 分区**——部分列更新要求 key 齐全，而支付/退款事件拿不到订单的 `create_time`。见 [08](./08-问题索引.md) D20 / E20 / E31。

**退款口径：** 源端一单一退款（`refund_id = order_id`），所以退款分支直接覆盖 `refund_amount`，不需要 SUM；`0 申请 / 2 处理中 / 3 拒绝` 的流水不写，避免把没退成的钱算进退款额。

**退款双口径怎么落：** [02-指标体系](./02-指标体系.md) 要求实时按"退款发生时间"、离线对账按"原订单时间"。实现上**只存一份退款事实，两个口径都在 DWD 上算**：

| 口径 | 算法 | 落到哪 |
|---|---|---|
| 退款发生时间（实时看板、退款率） | `refund_amount` 按 `refund_time` 归日 | 聚合进 `dws_trade_1min.refund_amt` |
| 原订单时间（T+1 对账、结算 GMV） | 同一行 `refund_amount` 按 `create_time` 归日 | 不落实时表，对账时在 DWD 上跑 T-1 聚合 |

所以 DWS 的 `refund_amt` 只有"发生时间"一个口径，不存在两套字段。对账不查 DWS，而是用 DWD 的 `create_time` + `refund_amount` 重算——这也是累积快照表必须同时保留 `create_time` 和 `refund_time` 的原因。

**另外两种事实表类型（要能对比）：**

| 类型 | 特征 | 适用 |
|---|---|---|
| 事务事实表 | 一行一个事件，只追加 | 支付流水、埋点 |
| 周期快照事实表 | 一行一个周期，如每日库存 | 库存、账户余额 |
| **累积快照事实表** | 一行一个实体，多里程碑更新 | 订单、工单、物流单 |

### 5.2 `dwd_traffic_detail`：事务事实表

| 字段 | 说明 |
|---|---|
| `event_id` | 事件唯一 ID，去重依据 |
| `user_id`, `product_id`, `session_id` | |
| `event_type` | `page_view` / `add_cart` / `order_submit` |
| `event_time` | 事件时间，用于水位线与窗口 |
| `dt` | |

清洗规则：按 `event_id` 去重（埋点重发 5%）、过滤 `event_type` 非法值、`event_time` 越界的丢弃。脏数据不丢，写 `dwd_dirty_record`。

**已落地（2026-11-25，J4）**：建表 `sql/06_init_doris_traffic.sql`，作业 `flink/sql/j4_dwd_traffic.sql`。Doris 实际 key 是 `UNIQUE KEY(event_id, dt)`（分区列必须是 key 列，08 E15），`enable_unique_key_merge_on_write=true`：同一 `event_id` 的重复发送后写覆盖先写，查询直接是一行，不需要额外去重表。`dt` 取 `event_time` 日期，动态分区今天 ~ +3 天、保留 90 天，8 桶。

`dwd_dirty_record` 用 **Duplicate Key(dt, rule_id, source_table, biz_key)**，只追加不去重；当前 `rule_id` 只有 `Q04`（`event_time` 超出 `[now-30d, now+5min]`）和 `Q05`（`event_type` 非法、`event_id`/`user_id` 缺失），`reason` 写具体判定，`raw_data` 是 JSON 解析后重构的字段快照。**`dt` 取拦截当天（处理时间）而不是事件日期**：Q04 的历史越界事件可能早于建表日期，按事件日期写会因分区不存在而 load 失败；按天出脏数据率也应以"哪天发现的"为准（08 D23）。

冒烟结果（`scripts/smoke_j4.sh`）：合法事件一次可见、`event_time` 与发送值一致；同一 `event_id` 发两次 DWD 只有 1 行；非法枚举落 Q05、早 40 天的事件落 Q04；清理后残留 0 行。压测实测 200 QPS 连续 269.8 秒，DWD 落 50,320 行且 `COUNT(*) = COUNT(DISTINCT event_id)`，脏数据 Q04 61 / Q05 51，与注入量（67 / 56）的差额是 J4 晚于生成器启动的窗口。

### 5.3 三张 DWS 表（J3 落地，2026-11-25）

三张表都是 Aggregate Key，分区 `dt` 必须在 key 里（08 E15），所以 Doris 的实际 key 比业务粒度多一个 `dt`。度量列全部 `SUM`，维度列 `REPLACE_IF_NOT_NULL`——`SUM` 会跳过 NULL，正好支持"三条流各写各的度量列"；`REPLACE` 会被 NULL 冲掉，所以维度列不能用它（08 E21）。

| 表 | Doris key | 度量列 | 维度（退化） |
|---|---|---|---|
| `dws_trade_1min` | `(dt, stat_minute)` | `order_cnt`, `order_amt`, `pay_cnt`, `pay_amt`, `refund_cnt`, `refund_amt` | — |
| `dws_trade_shop_1h` | `(dt, stat_hour, shop_id)` | 同上六项 | `province`, `city`（Lookup `dim_shop`，支付/退款分支由 DWD 带出） |
| `dws_trade_product_1h` | `(dt, stat_hour, product_id)` | `order_cnt`, `item_cnt`, `order_amt`, `pay_cnt`, `pay_amt` | `product_name`, `category_id`, `category_name`, `brand`（Lookup `dim_product`） |

口径与取舍：

- `stat_minute` / `stat_hour` 都按**事件时间**截断，不是处理时间；退款按 `refund_time` 归桶，与 5.1"退款双口径"里的实时口径一致。
- 一笔订单多件商品时，`dws_trade_product_1h.order_cnt` 是**明细行数**，`item_cnt` 才是件数；`order_amt` 用明细 `amount` 合计，因此 `order_amount=0` 的异常单也按明细计入，和 02 的 GMV 口径不冲突。
- 商品级支付金额来自 `ods_order_detail` ⋈ `ods_payment`（下单后 1 小时内支付）；退款不摊到商品（退款是订单级）。1 小时外的迟到支付在商品级会漏，分钟/店铺级不受影响——它们直接消费支付事件。
- 支付/退款事件的店铺归属靠 Lookup `dwd_trade_order_detail` 补齐；DWD 行未到时落 `shop_id = -1`，不会让整批 load 因 key 为 NULL 失败，但那一笔记到"未知店铺"。

### 5.4 两张流量 DWS 表（J5 落地，2026-11-25）

| 表 | Doris key | 度量列 |
|---|---|---|
| `dws_traffic_1min` | `(dt, stat_minute)` | `pv` / `cart_cnt` / `submit_cnt`（`SUM`）、`uv`（`BITMAP_UNION`） |
| `dws_user_1d` | `(dt, stat_date)` | `uv` / `cart_uv` / `submit_uv`（都是 `BITMAP_UNION`） |

口径与取舍：

- **一行里混着两类行。** 分钟表既要窗口指标（pv / 加购 / 下单次数），又要 UV 的用户集合，而 bitmap 只能由 Doris 侧构造。做法是同一个 sink 写两种行：窗口聚合行带指标、`uv_id` 为 NULL；同一窗口再按 `user_id` 分组写 UV 行（`pv=0`、`uv_id=user_id`）。`SUM` 加 0 不变，`BITMAP_UNION` 遇到空 bitmap 不变，互不污染。UV 行必须和指标行在同一个窗口里，否则迟到事件会只进 UV 不进 pv，出现 `uv > pv`（08 E26）。
- **分钟表只看水印内事件。** 超过水印的迟到数据（默认注入 1%）不进分钟表，日表 `dws_user_1d` 不设窗口、收全量，所以“日 UV 与 DWD 完全一致、分钟表可能略少”。另有一类脏时间戳会提前推高水位线，见 08 E27。
- **pv 用 `COUNT(DISTINCT event_id)`，不是 `COUNT(1)`。** DWD 用 Unique Key 把重发事件覆盖掉，DWS 必须同口径，否则 pv 会比 DWD 多出约 5%（Q08 的注入比例）。
- **UV 的 bitmap 存 `user_id`。** 查询用 `bitmap_union_count`；按维度切片时对 bitmap 求并集即可，不会像“人数相加”那样重复计人（八节）。
- **`dws_user_1d` 只覆盖埋点侧三个用户集合**（浏览 / 加购 / 提交下单）。支付用户不在埋点流里，实时侧从 `dwd_trade_order_detail` 的 `pay_time` 算，对账口径见 [06](./06-数据质量与对账.md) 6.1。
- 写入靠 Stream Load 的 `columns` 表达式 `uv=to_bitmap(uv_id)`；Flink 只输出整数用户 ID。`to_bitmap(NULL)` 得到空 bitmap，实测见 [08](./08-问题索引.md) E25。

### 5.5 三张 ADS 表（J6 落地，2026-11-25）

ADS 是看板直接查的结果层，三张表都由 `sql/08_init_doris_ads.sql` 建表，`scripts/run_j6.sh` 从 DWS 刷新（Doris SQL 批刷新，每 60 秒一次，不占 Flink 槽位，原因见 [08](./08-问题索引.md) D26）。

| 表 | Doris key | 粒度 | 字段 |
|---|---|---|---|
| `ads_gmv_realtime` | `UNIQUE KEY(dt, stat_minute)` | 分钟 | `order_cnt` / `order_amt` / `pay_cnt` / `pay_amt` / `pay_user_cnt` / `refund_cnt` / `refund_amt` / `net_amt` / `pay_rate` / `avg_user_amt` |
| `ads_conversion_funnel` | `UNIQUE KEY(dt, stat_date)` | 日 | `pv` / `cart_cnt` / `submit_cnt` / `uv` / `cart_uv` / `submit_uv` / `pay_user_cnt` / `cart_rate` / `submit_rate` / `pay_rate` |
| `ads_topn_product` | `UNIQUE KEY(dt, stat_date, rank_no)` | 日 + 排名 | `product_id` / `product_name` / `category_id` / `category_name` / `brand` / `order_cnt` / `item_cnt` / `order_amt` / `pay_cnt` / `pay_amt` |

口径与取舍：

- **全量覆盖写，重复执行幂等。** 每次只重算一天（默认今天），Unique Key 后写覆盖先写；补历史用 `--dt`。`ads_topn_product` 额外先 `DELETE` 当天，否则商品掉出 TOP 10 后旧排名行会残留。
- **TOP N 是 ADS 里唯一的聚合。** 把 `dws_trade_product_1h` 当天的商品行按 `product_id` 求和后 `ROW_NUMBER()`，取前 10；排名写进 `rank_no`，看板按它排序。这与"ADS 只取数不聚合"的原则有偏差，但排名必须看全量，见一节第 3 条。
- **`pay_user_cnt` 是 ADS 唯一回读 DWD 的字段。** DWS 只存了流量侧三个用户 bitmap，没有支付用户集合，所以按 `dwd_trade_order_detail.pay_time` 去重人数（过滤 `is_deleted = 0`）。其余字段全部来自 DWS。
- **分钟表是"分钟口径"。** `pay_rate`、`avg_user_amt` 的分母只覆盖该分钟，不能当天的支付转化率/客单价用；日客单价 = `SUM(ads_gmv_realtime.pay_amt) ÷ ads_conversion_funnel.pay_user_cnt`。
- **漏斗的分子/分母来自两个不同事实集合。** `pay_user_cnt` 来自交易 DWD（真实支付），`submit_uv` 来自埋点（提交按钮）；两者不是严格包含关系，`pay_rate` 可能大于 1，仅作趋势参考。另 `pv / cart_cnt / submit_cnt` 来自分钟 DWS，受水位线限制（08 E27），UV 系列来自日表，收全量。
- 实测（2026-11-25，`scripts/smoke_j6.sh`）：造一单 50.00（20.00 + 30.00）后，下单分钟 `1 / 50.00`、支付分钟 `1 / 50.00 / 1 / 50.00 / 50.00 / 1.0000`；TOP N 为 30.00 第 1、20.00 第 2；漏斗 7 个计数与 DWS/DWD 重算值逐字段相等；清理后 ADS 无残留。

## 六、维度建模要点

### 6.1 星型模型

`dwd_trade_order_detail` 为中心事实表，`dim_product` / `dim_user` / `dim_shop` 围绕，构成星型。不用雪花模型，因为品类层级只有一层，拆表只会增加 join。

### 6.2 维度退化

`province` / `city` 直接冗余在订单宽表里，不通过 `dim_shop` join。理由：

- 省份是高频分析维度，join 成本高
- 店铺省份基本不变，退化不会失真
- 这是"维度退化"的标准用法

**注意：** 商品类目不能退化，因为商品可能改类目，必须以订单发生时的维度为准（快照语义）；这也是为什么 DWD 在打宽时要取**下单当天**的 `dim_product` 分区，而不是最新分区。

**落地偏差（2026-11-25，`dim_shop`）：** 4.1 定的"每日全量快照 + `dt` 分区"在 Doris 里没有照搬，`dw.dim_shop` 实际是 **`UNIQUE KEY(shop_id)` 的最新快照**（只多一个 `snapshot_date` 列标记快照日期），建表见 `sql/03_init_doris_dim.sql`。

原因：J2 用 Flink Lookup Join 按 `shop_id` 点查维表，要求**一个 key 只命中一行**；若按 `dt` 分区，同一个 `shop_id` 在库里有多天数据，lookup 会返回多行，关联结果直接膨胀。而 Doris 维表 lookup 又不支持"只查某个分区"，所以做不成"取订单当天快照"。店铺所在省市基本不变（本节第一条理由），只留最新快照不会失真。

**落地偏差（2026-11-25，`dim_product`）：** 上面说的"做 J3 时用带 `dt` 分区的维表 + 显式分区条件解决"没有实现——Flink 的 Lookup Join 只发 `WHERE product_id IN (...)`，拼接不了分区条件，带 `dt` 分区后同一个 `product_id` 必然命中多行。J3 落地时 `dw.dim_product` 同样退化成 **`UNIQUE KEY(product_id)` 最新快照 + `snapshot_date`**（`sql/05_init_doris_dim_product.sql`，5 万行由 `scripts/load_dim_product.sh` 装载）。代价是商品改类目后，历史订单会按最新类目归因；成交价不受影响，因为下单时的价格快照存在 `order_detail.price`，不在维表里。见 08 D22。

### 6.3 打宽时点

- 订单宽表：取 `create_time` 当天的 `dim_product`、`dim_shop`
- 这样保证"历史订单用的是当时的维度"，与离线口径一致

## 七、Doris 模型选型

| 表 | Doris 模型 | 关键参数 | 理由 |
|---|---|---|---|
| ODS 四张 | **Duplicate Key** | — | 保留全部变更，可回溯 |
| DIM 三张 | **Unique Key（merge-on-write）** | `enable_unique_key_merge_on_write = true` | 主键覆盖，点查快 |
| `dwd_trade_order_detail` | **Unique Key（MoW）** | `UNIQUE KEY(order_id)`、sink 侧 `partial_columns`，**不设 sequence_col**（E31） | 三条流各写各的列，靠部分列更新合并；key 只有 `order_id`，故不分区（D20） |
| `dwd_traffic_detail` | **Unique Key（MoW）** | `UNIQUE KEY(event_id, dt)`、`enable_unique_key_merge_on_write` | 天然去重；分区列必须是 key 列，故带上 `dt` |
| `dwd_dirty_record` | **Duplicate Key** | `DUPLICATE KEY(dt, rule_id, source_table, biz_key)` | 拦截记录只追加、不去重，按 `dt + rule_id` 出日报 |
| `dws_trade_*` | **Aggregate Key** | `SUM` / `REPLACE_IF_NOT_NULL` | 预聚合，查询快；维度列不能被 NULL 冲掉 |
| `dws_traffic_1min` / `dws_user_1d` | **Aggregate Key + BITMAP** | `uv` 用 `BITMAP_UNION` | 去重可上卷 |
| ADS 三张 | **Unique Key（MoW）** | `enable_unique_key_merge_on_write = true` | 结果覆盖写入，`DELETE` 可用于 TOP N 当天重排 |

**为什么 DWS 用 Aggregate 而不是 Unique：** Aggregate 模型在写入时就做聚合，查询不需要再 `GROUP BY`，看板查询是毫秒级。代价是不能查明细，但 DWS 本来就不需要明细。

## 八、UV 去重方案：Doris bitmap

**选 Doris `bitmap`，不用 Flink 状态去重。**

| 方案 | 问题 |
|---|---|
| Flink 状态去重 | 状态随用户数膨胀；跨天要清理；无法按维度上卷 |
| **Doris bitmap**（选它） | 建表时 `uv` 列为 `BITMAP`，写入 `to_bitmap(user_id)`，查询 `bitmap_union_count` |

决定性理由是**可上卷**：分省 UV 相加会重复计人，但 bitmap 求并集是精确的。这样 `dws_user_1d` 可以按任意维度组合切片，全站 UV 直接由各省 bitmap 并集得出。

## 九、分区、分桶与生命周期

### 9.1 分区

按天 `PARTITION BY RANGE(dt)`，开动态分区：

```sql
"dynamic_partition.enable" = "true",
"dynamic_partition.time_unit" = "DAY",
"dynamic_partition.start" = "-90",
"dynamic_partition.end" = "3",
"dynamic_partition.prefix" = "p",
"dynamic_partition.buckets" = "4"
```

**例外：`dwd_trade_order_detail` 不分区**（2026-11-25）。累积快照靠部分列更新合并三条流，key 只能是 `order_id`（支付/退款事件没有订单的 `create_time`，拿不到 `dt`），而 Doris 要求分区列必须是 key 列，所以这张表只能不分区、按 `order_id` 分桶。数据量 90 万行、查询基本按 `order_id` 或 `dt` 过滤，单表全扫可接受；要恢复分区就得改成"支付/退款事件也带 `dt`"，那需要回查订单，属于更大的改动。理由与验证见 [08](./08-问题索引.md) D20 / E20。

### 9.2 分桶

单 BE 单机环境，分桶数控制在 **4~8**，避免小文件过多：

| 表 | 分桶键 | 桶数 |
|---|---|---|
| `dwd_trade_order_detail` | `HASH(order_id)` | 8 |
| `dwd_traffic_detail` | `HASH(event_id)` | 8 |
| `dwd_dirty_record` | `HASH(biz_key)` | 4 |
| DWS / ADS | `HASH(stat_minute)` 等 | 4 |

**分桶数不是越多越好：** 单机 8 桶已经能打满查询并行度，再大只会增加 compaction 压力。这一点可以结合 `-235 Too many versions` 一起看。

### 9.3 生命周期

| 层 | 保留 | 理由 |
|---|---|---|
| ODS | 7 天 | 只用于排查，快速回放 |
| DWD | 30 天 | 支撑 30 天复购率 |
| DWS | 90 天 | 看板同比环比 |
| DIM | 全量 + 90 天快照 | 回溯历史维度 |
| ADS | 90 天 | 小表，且能从 DWS 重算；与动态分区 `-90` 一致 |

## 十、指标 → 表映射

| 指标 | 来源表 | 计算方式 |
|---|---|---|
| 支付 GMV | `dws_trade_1min` / `_shop_1h` / `_product_1h` | `SUM(pay_amt)` |
| 支付笔数 | 同上 | `SUM(pay_cnt)` |
| 退款金额 | 同上 | `SUM(refund_amt)` |
| 支付转化率 | `ads_gmv_realtime` | `pay_cnt ÷ order_cnt`（分钟口径） |
| 客单价 | `ads_gmv_realtime` + `ads_conversion_funnel` | 日客单价 = `SUM(pay_amt) ÷ pay_user_cnt`；分钟行里的 `avg_user_amt` 只覆盖该分钟 |
| 当日 UV | `dws_user_1d` | `bitmap_union_count(uv)` |
| 复购率 | `dws_user_1d` | 购买次数 ≥2 的用户占比 |
| 漏斗 | `ads_conversion_funnel` | 各事件类型去重人数 |
| TOP N 商品 | `dws_trade_product_1h` → `ads_topn_product` | 按 `product_id` 汇总 GMV 后排序，rank 落 ADS |

## 十一、已知取舍

1. 单一订单表承载全部里程碑，写入是整行覆盖，`update_time` 判断放在 Flink 侧。若并发更新频繁，需要改成"部分列更新"（Doris `partial_update`），本项目数据量下不必要。
2. 维表用每日快照，跨天回溯要看 `dt` 分区，查询时必须带 `dt` 条件，否则会扫全表。
3. 离线链路以 MySQL 为权威源，不以 Kafka 为源——对账的基准必须是业务库，Kafka 只能算"实时侧的输入"。
