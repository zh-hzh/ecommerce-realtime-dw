## 二、为什么是 Lambda，不是 Kappa

| 维度 | Lambda（选它） | Kappa |
|---|---|---|
| 链路 | 实时 + 离线两条 | 只有流处理一条 |
| 准确性 | 离线做 T+1 精确结算 | 依赖事件回放重建 |
| 对账 | 天然有两个独立结果可比 | 自己和自己比，无法发现系统性偏差 |
| 成本 | 多维护一条离线链路 | 链路短 |

选 Lambda 的唯一决定性理由：**对账需要两个独立的计算结果**。Kappa 架构下只有一个结果，没法证明它对不对。而"我怎么保证实时数据可信"正是这个项目要回答的核心问题。

代价是离线链路要额外维护，但 Spark + Hive 你已有两个项目的基础，成本可控。

## 三、组件职责边界

| 组件 | 只负责 | 不负责 |
|---|---|---|
| MySQL | 产生权威交易数据 | 分析查询 |
| Flink CDC | 抓 binlog 写入 Kafka | 清洗、聚合 |
| Kafka | ODS 缓冲与解耦、保证分区内有序 | 长期存储（7 天） |
| Flink SQL | 清洗、打宽、聚合、写 Doris | 数据服务 |
| Doris | 存储与 OLAP 查询 | 数据加工 |
| Spark + Hive | T+1 精确重算 | 秒级查询 |
| DolphinScheduler | 调度维表快照、离线作业、对账、质量巡检 | 流作业的提交、重启与恢复 |

**一条原则：每一层只做一件事。** CDC 作业里不写清洗逻辑，聚合不在 Doris 里做，看板只查 ADS。

## 四、数据链路与作业划分

### 4.1 Kafka topic 设计

| topic | 分区 | Key | 保留 | 用途 |
|---|---|---|---|---|
| `ods_order` | 3 | `order_id` | 7 天 | 订单变更 |
| `ods_order_detail` | 3 | `order_id` | 7 天 | 订单明细（只追加） |
| `ods_payment` | 3 | `order_id` | 7 天 | 支付流水 |
| `ods_refund` | 3 | `order_id` | 7 天 | 退款流水 |
| `ods_traffic` | 6 | `user_id` | 7 天 | 埋点事件 |

**Key 一律用业务主键**：同一个 `order_id` 的多次变更必然落在同一分区、同一条消费流里，顺序不乱。这是解决乱序的第一道防线，比在 Flink 里靠 `update_time` 兜底更根本。

**为什么单独给明细一个 topic：** MySQL 有 7 张表，其中 `order_detail` 只在下单时插入一次、之后不变。它不参与订单状态机，但实时侧要算"商品粒度 GMV / TOP N 商品"就必须有它。放进 `ods_order` 会把两种 schema 混在一条流里，所以单开 `ods_order_detail`，同样用 `order_id` 做 key，保证同一订单的明细与主单落在同一分区。

分区数决定并行度上限：订单类 3 个分区 → Flink 并行度最多 3；流量 6 个 → 最多 6。

**为什么订单类只给 3 个分区：** 日常订单量是 20 单/分钟，3 个分区绰绰有余；压测只压埋点（2000 QPS，6 个分区），订单链路不是瓶颈。所以 3 并行度够用，不构成"压测压不上去"的问题。

**真要扩订单并行度，只能重建 topic：** 加分区会打乱 `key` 到分区的映射，同一 `order_id` 的历史数据仍留在旧分区、新数据去新分区，顺序保证失效。流程是"建新 topic → 作业双写 → 存量回放 → 切读新 topic → 删旧 topic"，需要短暂停写。这是 [05-数据源与造数](./05-数据源与造数.md) 里写"分区数不要事后改"的实际含义。

### 4.2 作业清单

| 编号 | 作业 | 输入 | 输出 | 并行度 | 类型 |
|---|---|---|---|---|---|
| J1 | `cdc2kafka` | MySQL binlog | Kafka 四个交易 topic（`ods_traffic` 由埋点生成器写） | 1 | 流 |
| J2 | `dwd_trade` | ods_order/payment/refund/detail + DIM | `dwd_trade_order_detail` | 3 | 流 |
| J3 | `dws_trade` | ODS 交易三流 + `ods_order_detail` + Lookup `dwd_trade_order_detail` / `dim_shop` / `dim_product` | `dws_trade_1min` / `_shop_1h` / `_product_1h` | 3 | 流 |
| J4 | `dwd_traffic` | `ods_traffic` | `dwd_traffic_detail` + `dwd_dirty_record` | 6 | 流 |
| J5 | `dws_traffic` | `ods_traffic`（复用 J4 清洗条件，见 D21） | `dws_traffic_1min` / `dws_user_1d` | 3 | 流 |
| J6 | `ads_refresh` | Doris 的 DWS 三张表 | `ads_*` 三张 | — | 定时批（Doris SQL，每 60 秒） |
| O1 | `offline_t1` | MySQL | Hive DWD/DWS/ADS | — | Spark 批 |
| O2 | `reconcile` | Hive ADS + Doris ADS | `ads_reconcile_diff` | — | SQL |

**J2 是核心难点**：订单 / 支付 / 退款三条流要合并成"一行一单"的累积快照，再 Lookup Join 维表打宽。这里同时涉及多流合并、维表关联、幂等更新三件事。最终没走 interval join：订单里程碑跨度最长 20 天，窗口留不住，且订单流单独触发时拿不到支付/退款字段；改成**三条流各写各的列，Doris 部分列更新合并**（见下方第三版）。

**J2 分三版落地（2026-11-25）**：首版只接 `ods_order` 单流写 `dwd_trade_order_detail`，目的是先打通 Kafka → Flink → Doris 并验证实时可见与幂等更新，脚本为 `flink/sql/j2_dwd_trade.sql` + `scripts/run_j2.sh`，冒烟 `scripts/smoke_j2.sh`（插入/更新/软删三步都在 Doris 查到，各约 10~12 秒，受 10s checkpoint 约束）。

**第二版（2026-11-25）：`dim_shop` Lookup Join 补齐省市。** `dw.dim_shop` 由 `scripts/load_dim_shop.sh` 从 MySQL `shop_info` 全量导 2000 行（mysql 导 TSV → curl Stream Load 到 FE），J2 SQL 里源表加 `proc_time AS PROCTIME()`，用 `LEFT JOIN dw.dim_shop FOR SYSTEM_TIME AS OF o.proc_time` 点查维表，`province`/`city` 不再是 NULL。lookup 缓存 5000 行 / 10 分钟，单行命中不会膨胀。冒烟脚本同步加了断言：测试单 `shop_id=1` 的省市必须与 MySQL 一致（实测 `广东 / 佛山`），插入约 4~6 秒可见，更新/软删约 12 秒可见。支付/退款字段仍是后续增量。

**第三版已落地（2026-11-25）：支付/退款并入 DWD。** 作业里三条流各写各的列，用 `EXECUTE STATEMENT SET` 提交为同一个作业：订单分支写订单字段 + 省市，支付分支写 `pay_id/pay_amount/pay_status/pay_time`（只取成功支付），退款分支写 `refund_amount/refund_time/refund_status`（只取成功退款）。Doris 侧 `partial_columns=true`，每个 sink 的 Flink DDL 只声明自己那几列，`sink.properties.columns` 只列这几列——**列没列进去就不动，列进去了但 JSON 缺 key 会被置 NULL**（实测见 08 E20）。三个 sink 各自独立的 label 前缀（`j2_order_v3` / `j2_pay_v3` / `j2_refund_v3`）。据此 DWD 表的 key 从 `(order_id, dt)` 改为 `order_id`、取消 `dt` 分区（D20）。**表上不设 `function_column.sequence_col`**：三个 sink 在同一个 checkpoint 内提交顺序不保证，sequence 会把"较晚提交的支付/退款部分列更新"整行丢掉（实测 149 笔支付丢 113 笔，08 E31）；三组列不重叠，MoW 后写覆盖即可。冒烟覆盖"下单 → 支付 → 退款 → 软删"四段，每段都断言前一段的列没被冲掉，实测每段约 10~12 秒可见。

**J3 的商品粒度来自明细流，不是 DWD。** DWD 是订单粒度的累积快照，一个订单多件商品塞不进去。`dws_trade_product_1h` 消费 `ods_order_detail` 再 Lookup `dim_product` 取类目品牌，按 `stat_hour + product_id` 累加下单与支付金额，供实时 TOP N 商品和分品类 GMV 使用。

**J3 已落地（2026-11-25）：三张 DWS 表 + 商品维表。** 脚本 `flink/sql/j3_dws_trade.sql` + `scripts/run_j3.sh`，冒烟 `scripts/smoke_j3.sh`；建表 `sql/04_init_doris_dws.sql`、`sql/05_init_doris_dim_product.sql`，商品维表装载 `scripts/load_dim_product.sh`（5 万行）。四条口径要点：

| 要点 | 做法 | 原因 |
|---|---|---|
| 输入不是 DWD | 读 Kafka 的 `ods_order/ods_payment/ods_refund/ods_order_detail`，DWD 只做 Lookup | Doris connector 没有 changelog 流，DWD 的更新不会推给 Flink（08 D21） |
| 只取新增事件 | 源表按 JSON 信封读 `after` + `op`，下单取 `op='c'`，退款取 `refund_status=1` 的 `c/u` | `debezium-json` 会把 UPDATE 解析成 `-U/+U`，聚合模型无法回退（消费者会重复计数） |
| 店铺归属 | 订单流直取 `shop_id` + Lookup `dim_shop`；支付/退款流 Lookup DWD 补 `shop_id`/省市，查不到落 `-1` | 支付/退款事件本身不含店铺字段；兜底 `-1` 不让整批 load 因 key 为 NULL 失败 |
| 商品支付金额 | `ods_order_detail` ⋈ `ods_payment`（下单后 1 小时内支付），金额按明细 `amount` 记账 | 明细流只有下单事件，拿不到"是否支付"；订单金额 = 明细合计（05 造数口径） |

Doris 侧三张表都是 **Aggregate Key**，分区列 `dt` 必须在 key 里，所以业务主键实际是 `(dt, stat_minute)` / `(dt, stat_hour, shop_id)` / `(dt, stat_hour, product_id)`。三条流各写各的度量列，靠 `SUM` 跳过 NULL 自然合并；维度列用 `REPLACE_IF_NOT_NULL`，避免 NULL 把已写好的省市/类目冲掉（实测见 08 E21）。分钟级与店铺级同时含下单、支付、退款六项度量，商品级含下单与支付五项。

冒烟实测（无业务写入时）：每个断言都在一次 checkpoint 周期内可见（2~12 秒）；下单 50.00、支付 50.00、退款 10.00 在三张表全部对上，商品级两件商品分别 20.00 / 30.00 全额对账，清理后 Doris 残留 0 行。

**J4 已落地（2026-11-25）：埋点流清洗与分流。** 输入 `ods_traffic`（6 分区，key `user_id`），由 `generator/gen_traffic.py` 持续写入；作业 `flink/sql/j4_dwd_traffic.sql` + `scripts/run_j4.sh`，冒烟 `scripts/smoke_j4.sh`；建表 `sql/06_init_doris_traffic.sql`（`dwd_traffic_detail` + `dwd_dirty_record`）。三条口径要点：

| 要点 | 做法 | 原因 |
|---|---|---|
| 去重 | 不建去重表，DWD 用 `UNIQUE KEY(event_id, dt)` + merge-on-write | 重复事件后写覆盖先写，天然一行；Q08 只计数不落脏表（06 三节） |
| 分流 | 同一 topic 建两张源表、两个 `group.id`，分别写明细与脏数据 | 同一 `group.id` 的两个 KafkaSource 会并入同一消费组把 6 个分区"分掉"，每条分支只能看到一部分消息 |
| 时间边界 | `event_time` 转 `TIMESTAMP_LTZ` 后与 `CURRENT_TIMESTAMP` 比，超出 `[now-30d, now+5min]` 落 Q04 | 迟到几分钟仍是合法数据；只有值本身越界才算脏数据。`CURRENT_TIMESTAMP` 在流模式逐条求值 |
| 脏数据日期 | `dwd_dirty_record.dt` 取**拦截当天** | Q04 的历史事件可能早于建表日期，按事件日期写会因分区不存在导致 load 失败（08 D23） |

冒烟实测：合法事件 `event_time` 与发送值一致；同一 `event_id` 发两次 DWD 仍 1 行；非法枚举落 Q05、早 40 天的事件落 Q04；清理后残留 0 行。压测用生成器 200 QPS 连跑 269.8 秒（53,957 条逻辑事件 / 56,649 条消息，注入重复 4.99% / 迟到 1.02% / 非法类型 0.10% / 越界时间 0.12%），J4 落 DWD 50,320 行且 `COUNT(*) = COUNT(DISTINCT event_id)`，脏数据 Q04 61 / Q05 51。最初并行度 6（等于 topic 分区数）；J5 上线前降到 3，把槽位让出来（D25）。

**2000 QPS × 30 分钟压测（2026-11-26）：单并行度 J4 就能追平。** 当时 J1×4 + J2 已占 7 个槽位，只剩 1 个，所以 J4 用**并行度 1** 起（`sink.label-prefix` 升到 v3，避开 E19），其余作业不动、离线链路不停机，阶梯 500 → 1000 → 2000 各预热 2 分钟后主压 1800 秒：

| 观测项 | 实测值 |
|---|---|
| 实际写入速率 | 500 档 525/s、1000 档 1051/s、2000 档稳定 2095~2107/s（含 5% 重复注入，逻辑量即 2000/s） |
| 消费 lag | 全程在 0~21k 之间随 10 秒 checkpoint 锯齿波动，**没有累积趋势**；停压后 3 秒追平到 0 |
| checkpoint | 232 次、0 失败；`checkpointDuration` p50 72 ms / max 100 ms，状态约 2.5 KB（Kafka 位点 + 2PC 事务，不含数据） |
| Doris 落库 | `dwd_traffic_detail` 新增 3,772,480 行；当日脏数据 Q04 3,706 / Q05 3,814（占 0.20%） |
| 资源 | 可用内存 10.9 → 8.9 GB，load 全程 1~2.8（32 核），无 OOM、无反压导致的重启 |

结论要带着前提读：**这是"单槽吞吐下限"的数据，不是 J4 的生产配置**。3 并行度、J1~J5 全部同时跑时的 2000 QPS 没有复测过，因为槽位预算 16 与实机 8 的差距（D25）决定了不可能全开再压；`ods_traffic` 6 个分区由 1 个消费者吃下也没成为瓶颈，说明瓶颈不在 J4。

**J5 已落地（2026-11-25）：流量 DWS 与 bitmap UV。** 作业 `flink/sql/j5_dws_traffic.sql` + `scripts/run_j5.sh`，冒烟 `scripts/smoke_j5.sh`；建表 `sql/07_init_doris_traffic_dws.sql`。四个要点：

| 要点 | 做法 | 原因 |
|---|---|---|
| 输入 | 直接消费 `ods_traffic`，复用 J4 的清洗条件 | Doris 表没有 changelog 流，Flink 读不到 DWD 的变更（D21）；脏数据仍只由 J4 落一次 |
| 次数去重 | pv / 加购 / 下单在 1 分钟窗口内用 `COUNT(DISTINCT event_id)` | 埋点重发在秒级到达，分钟窗口能覆盖；状态只留一个窗口，不随天数膨胀（Q08） |
| UV | `uv` / `cart_uv` / `submit_uv` 都是 `BITMAP`，用户集合由 Doris `BITMAP_UNION` 去重 | bitmap 可跨维度精确上卷，不用 Flink 状态（03 八节） |
| bitmap 写入 | Flink 侧输出 `uv_id`，Doris `columns` 头写 `uv=to_bitmap(uv_id)` | Flink 没有 bitmap 类型；官方 Connector 文档写法，NULL 得到空 bitmap（08 E25） |

分钟表一行里既有窗口指标行（`uv_id` 为 NULL、pv/cart/submit 为去重次数），也有 UV 行（pv 写 0、`uv_id=user_id`）；两者都来自同一个 1 分钟 TUMBLE 窗口，`SUM` 与 `BITMAP_UNION` 各自合并，互不影响。UV 必须和指标同窗口——第一版把 UV 按事件逐条写，超过水印的迟到事件只进 UV 不进 pv，出现过 `uv > pv` 的自相矛盾（E26）。分钟表因此只统计水印内事件，1% 的 5~30 分钟迟到不进分钟表；`dws_user_1d` 不设窗口、收全量，与 DWD 的全量口径一致。同一 topic 分两条流水线（分钟表、日表），各用独立 `group.id`（E22）。冒烟实测：2 个浏览用户 + 1 次加购 + 1 次下单、pv 重复发两次不翻倍，分钟 `pv=2 / cart=1 / submit=1 / uv=2`，日表三个 bitmap 各收各的用户（`bitmap_contains` 验证）；冒烟数据保留，与 DWD 同口径。压测实测：生成器 200 QPS 跑 180 秒（36,000 条逻辑事件 / 37,758 条消息，重复 4.9% / 非法类型 35 条，不注入迟到与越界时间），DWS 与 DWD 逐分钟比对 6 个分钟全一致（例如 `17:42:00` 的 `pv 10744 / cart 1015 / submit 229 / uv 10200` 两边完全相同）；日表 `uv / cart_uv / submit_uv = 27665 / 2886 / 738`，与 DWD 的 `COUNT(DISTINCT user_id)` 完全一致。

**J6 已落地（2026-11-25）：ADS 三张表由 Doris SQL 定时批刷新。** 建表 `sql/08_init_doris_ads.sql`，刷新逻辑 `sql/j6_ads_refresh.sql` + `scripts/run_j6.sh`（`--loop 60` 常驻，或交给 DS 触发），冒烟 `scripts/smoke_j6.sh`。为什么不是 Flink 流作业：Doris Connector 只提供有界 Source 与 Lookup，DWS 的变更不会推给 Flink（与 D21 同因）；16 个槽位已被 J1~J5 占满，再起常驻作业也没有位置。改成"每分钟一条 `INSERT ... SELECT` 覆盖写当天 ADS"，不占槽位、没有 checkpoint 状态，重复执行幂等（D26），看板延迟上限就是 60 秒。

口径：`ads_gmv_realtime` 从 `dws_trade_1min` 求和，`pay_user_cnt` 回读 DWD 按 `pay_time` 去重（过滤 `is_deleted=0`）；`ads_conversion_funnel` 的 pv / 加购 / 下单次数从分钟 DWS 求和，三个 UV 用 `bitmap_union_count`，支付用户同样回读 DWD；`ads_topn_product` 把 `dws_trade_product_1h` 当天行按商品求和后 `ROW_NUMBER()` 取前 10，写前先删当天，避免掉榜商品残留。实测（冒烟）：一单 50.00（20+30）落到下单分钟 `order_cnt=1 / order_amt=50.00`、支付分钟 `pay_cnt=1 / pay_amt=50.00 / pay_user_cnt=1 / net_amt=50.00 / avg_user_amt=50.00`；TOP N 30.00 第 1、20.00 第 2；漏斗 7 个计数与 DWS/DWD 重算值逐字段相等；清理后 ADS 残留 0 行，J2/J3 仍 RUNNING。

**O1 离线 T+1 已落地（2026-11-25）：MySQL 直读 → Hive 四层。** 建表 `sql/09_init_hive.sql`（`ods` / `dwd` / `dws` / `ads` 四库 10 张表，Parquet + `dt STRING` 分区），跑批 `spark/offline_t1.py` + `scripts/run_offline_t1.sh`，单个 `spark-submit --master local[2]`（YARN 未启动，见 E07）。四个要点：

| 要点 | 做法 | 原因 |
|---|---|---|
| 抽取来源 | Spark JDBC 直读 MySQL，按天范围读 `order_info` / `order_detail`，支付 / 退款按 `pay_time` / `refund_time` 当天范围读 | 对账基准必须是权威源（决策 #4），Kafka 有重复和迟到，不能当基准 |
| 支付 / 退款落 DWD | 抽取时 JOIN 订单，直接写 `dwd.dwd_payment_detail` / `dwd.dwd_refund_detail`，不保留裸流水 ODS | 单天分区拿不到跨天订单的 `user_id` / `is_deleted` / 下单时间，支付用户数与退款回溯都要它 |
| 写分区 | `INSERT OVERWRITE TABLE ... PARTITION (dt='xxx')`，每次跑一个 dt，重复跑结果不变 | 幂等；补历史就是逐天传 `--dt` |
| 时区 | `-Duser.timezone=Asia/Shanghai` + `spark.sql.session.timeZone` + JDBC `serverTimezone` | 不加会整体偏 8 小时，离线数直接不可比 |

**O2 对账已落地（2026-11-25）：Hive ADS × Doris 实时，5 个交易指标。** `spark/reconcile.py` + `scripts/run_reconcile.sh`：读 Hive `ads.trade_recon_1d` 的 dt 分区，用一条 `UNION ALL` SQL 从 Doris 取 5 个实时口径值（`dwd_trade_order_detail` 4 项 + `dws_trade_1min` 的 pay_amt），按 [06](./06-数据质量与对账.md) 6.2 判 PASS/FAIL，`append` 写 `dw.ads_reconcile_diff`（Unique Key 同日期同指标覆盖）。口径细节与正反向验证见 06 6.1 / 6.4。

**两条链路各自的取数边界：** 离线只跑"指定的那一天"，实时侧只覆盖"J1 启动之后"的变更。所以对账能做的日期 = 实时链路已运行的日期 ∩ 离线已跑过的日期；2026-11-24 及更早没有实时数据，不能对账（详见 06 6.5）。

**连接器已就位**（2026-11-25 实测）：`flink/lib` 下有 `flink-sql-connector-mysql-cdc-3.7.0-1.20.jar` 和 `flink-doris-connector-1.20-25.1.0.jar`，J1 与写 Doris 的作业都不缺包。离线侧不额外装驱动，复用 Hive lib 里的 `mysql-connector-j-8.0.33.jar`，由 `spark-submit --jars` 传入。

**J1 必须用 `scan.startup.mode=latest-offset`。** 库里已有 90 万历史单、298 万明细，若用默认的 `initial` 会先做全量快照，开局就把近 500 万行灌进 4 个交易 topic。历史数据只给离线链路用，实时链路只处理 J1 启动之后的变更。

**O2 对账不重跑流作业。** 两条链路各出一个 T-1 全天结果，再逐指标比：

| 侧 | T-1 结果从哪来 | 说明 |
|---|---|---|
| 实时 | Doris 的 `dt=T-1` 分区 | ADS/DWS 是全天覆盖写，日终后分区里就是 T-1 全天值；若有水位线外的迟到，在该分区上用 DWD 跑一条 T-1 聚合 SQL 修正 |
| 离线 | Hive 的 `dt=T-1` 分区 | Spark 从 MySQL 重算 |

两边都是批查，互不影响，**实时链路不中断**。真正回放 Kafka 只用于故障恢复，不用于日常对账——重放会重复写入，还得再清一遍。

**离线抽数用 Spark JDBC 直读 MySQL**，不经过 Kafka 也不落 HDFS 中转：对账基准必须是权威源（决策 #4），而 Kafka 里有重复和迟到，不能当基准。[05-数据源与造数](./05-数据源与造数.md) 里的 90 万历史单是直接 `INSERT` 进 MySQL 的，Spark 按天读出来就是完整的一天。

**7 张表全部走离线快照，包括 `order_detail`。** 明细在实时侧另有 `ods_order_detail` topic，但那只是流内的商品维度来源；离线链路的 `ods_order_detail` 是 Spark JDBC 按 `dt` 全量抽的 Hive 表，和质量巡检 C02 的订单-明细勾稽对得上。两条路同源（都来自 MySQL），互不依赖——实时明细丢了不影响离线，离线没跑也不影响实时。

**首次启动顺序不能颠倒**：先建表灌维表（`scripts/init_doris.sh` + `scripts/load_dim_shop.sh <mysql_root_password>`），再启 J2。否则 Lookup Join 全命中不到维表，订单的省市为 NULL——不丢单，但首日的分省分析全废。

### 4.3 调度职责（DolphinScheduler）

**定位：只做批编排，不做流调度。** 下面四个节点不是四份独立调度，而是**一条工作流 `nightly_t1` 的四个串行步骤**——DS 在这里是编排器，不是定时器。

| 任务 | 内容 | 跑批顺序 | 上游依赖 |
|---|---|---|---|
| `dim_snapshot` | MySQL → Doris 三张维表快照 | ① | 无 |
| `offline_t1` | MySQL → Hive ODS/DWD/DWS/ADS | ② | `dim_snapshot` 完成 |
| `reconcile` | Hive ADS × Doris ADS → `ads_reconcile_diff` | ③ | `offline_t1` 完成 |
| `quality_check` | 5 类规则跑批 → 写脏数据表 / 出日报 | ④ | `reconcile` 完成 |
| `backfill` | 按日期区间重跑指定分区 | 手动，独立 | 无 |

**不用 cron 定时。** 这台机器是个人电脑，凌晨不在线，写死"每日 04:00"的对账永远不会被执行。所以四个步骤做成一条**手动触发**的工作流 `nightly_t1`：

| 事项 | 做法 |
|---|---|
| 触发 | 开机后打开 DS，手动运行一次 |
| 日期参数 | 默认 `dt = T-1`，对账确认的是"昨天那一整天" |
| 断档补跑 | 连续几天没开机，填 `start_dt` / `end_dt`，按日期逐个实例跑 |
| DS 自动补数 | 不依赖。DS 的补数是手动点的，机器没开时不会自己长出来 |

对账是否准确只取决于"取的是 T-1 分区"，与几点触发无关；真正要守的是"跑完就冻结当天结论，之后重跑以新结果为准"（见 [06-数据质量与对账](./06-数据质量与对账.md) 6.3）。

**依赖按"数据就绪"判断，不按 cron 硬等。** 每个下游任务启动前先探测上游产物是否可用（Hive 分区是否存在、Doris 表当日分区是否有数据），不可用则失败退出而不是继续跑。按时间死等会在上游延迟时读到空分区，产出脏数据。

**DS 不负责的三件事：**

| 不做 | 原因 |
|---|---|
| 提交或重启实时作业 | Flink 靠 checkpoint + `restart-strategy` 自愈，不需要外部拉起 |
| 分钟级及以下的调度 | DS 是批调度器，不适合流任务节奏 |
| 实时作业之间的编排 | 实时作业顺序由 Kafka topic 与消费关系天然决定 |

这一条要在设计说明里讲清楚：**调度器不是流计算的高可用方案。** 流作业的恢复依赖 checkpoint 与状态后端，不依赖每分钟探测。

**落地顺序：先脚本，后编排。** 这五个任务每一个都跨组件，先在命令行跑通再搬进 DS：

| 任务 | 先手工跑通的东西 | 搬进 DS 后只管 |
|---|---|---|
| `dim_snapshot` | 一条 JDBC 抽数 + Stream Load 的脚本 | 触发时间、失败重试 |
| `offline_t1` | 一个 `spark-submit`（JDBC 读 MySQL → 写 Hive 分区） | 依赖 `dim_snapshot` |
| `reconcile` | 两条 SQL（Doris 侧、Hive 侧）+ 一条写差异表的 SQL | 依赖 `offline_t1` |
| `quality_check` | 每条质量规则一条 SQL，结果 `INSERT` 质量表 | 依赖 `reconcile` |
| `backfill` | 带日期参数的同一套脚本 | 无 |

**落地进度（2026-11-26）：`nightly_t1` 已建并跑通。** DS 以 standalone 单进程起，元数据从默认的 H2 内存库改到 MySQL 的 `dolphinscheduler` 库（重启不丢工作流），注册中心用 `jdbc` 不吃 ZooKeeper；建工作流走 REST 脚本 `scripts/ds_build_nightly_t1.py`（可重复执行、建完自动上线并触发）。四个节点全部是 Shell，调仓库里的现成入口，`dt` 是全局参数默认 `$[yyyy-MM-dd-1]`。实测实例 18：`dim_snapshot` → `offline_t1` → `reconcile` 三个节点 SUCCESS，`quality_check` 因 11-25 带注入金额异常而继承出口码 1、按设计阻断（D33）。三个启动期坑（H2→MySQL 的 schema 初始化、未上线不能触发、`sudo -i` 丢环境变量）见 08 E36。`backfill` 仍走 DS 的补数入口，没有单独建流。

这样出问题时能绕过 DS 单独重跑某一步，排错半径小；DS 只是编排器，不承载业务逻辑。**当前进度（2026-11-25）：`offline_t1` 与 `reconcile` 两步已能手工跑通；`dim_snapshot`（Doris 维表由 `load_dim_*.sh` 承担）、`quality_check`、`backfill` 仍只有设计；DS 已安装但未启动，`nightly_t1` 未建，本期不做编排（D28）。**

> 易混点：DS 自带 Flink 任务类型，但那是"作业部署与生命周期管理"，属于平台能力，不是"流调度"。生产上常见，本项目不使用。

## 五、关键决策记录

| # | 决策 | 放弃的方案 | 理由 |
|---|---|---|---|
| 1 | CDC 用 Flink CDC 3.x | Canal / Maxwell | 不用额外部署组件；与 Flink 同栈；全量 + 增量一体 |
| 2 | CDC 先写 Kafka，再由 Flink SQL 读 | CDC 直写 Doris | 解耦；Kafka 可被多个下游消费；出问题能重放 |
| 3 | ODS 放 Kafka，不放 Doris | ODS 也落 Doris | Kafka 是天然的追加日志；Doris 存 ODS 只会放大 compaction 压力 |
| 4 | 离线以 MySQL 为基准 | 从 Kafka 落湖再算 | **对账基准必须是权威源**；Kafka 有丢失和重复，不能当基准 |
| 5 | Flink SQL 而非 DataStream | Java DataStream | 社区主流写法；迭代快；窗口与 join 表达力足够 |
| 6 | UV 用 Doris bitmap | Flink 状态去重 | 可跨维度精确上卷；状态不会无限膨胀 |
| 7 | 维表每日全量快照 | 实时 CDC 维表 | 维表变更低频；快照可回溯；实现简单 |
| 8 | DWS 用 Aggregate 模型 | Unique 模型 | 写入即聚合，查询快；DWS 不需要明细 |
| 9 | Kafka 用 KRaft（broker + controller 合一） | ZooKeeper 模式 | 3.x 起 KRaft 已生产可用；少一个组件、少一套选举逻辑；ZooKeeper 模式官方已宣布逐步移除 |
| 10 | 所有服务监听绑 `127.0.0.1` | 绑 `0.0.0.0` 或宿主网卡 | 宿主 WLAN 为 DHCP，绑网卡地址会随 IP 变化失效 |

## 六、一致性设计

### 6.1 端到端语义

| 环节 | 保证 | 手段 |
|---|---|---|
| Kafka → Flink | 精确一次 | checkpoint 时提交 offset |
| Flink → Doris | 精确一次 | Doris connector 两阶段提交（2PC） |
| 兜底 | 幂等 | 主键 + MoW 后写覆盖（三组列不重叠），重复写入结果不变；DWD 不设 sequence，见 08 E31 |

两层设计：**2PC 保证不重不漏，幂等保证即使重了也不出错。** 被问到"怎么保证数据不重"时，要能同时讲出这两层。

### 6.2 checkpoint 配置

```yaml
execution.checkpointing.interval: 60s
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.timeout: 10min
state.backend.type: rocksdb
execution.checkpointing.min-pause: 30s
```

选 RocksDB 而不是内存：`dws_user_1d` 的 UV 集合和 interval join 的缓冲都在状态里，内存撑不住压测量级。

### 6.3 迟到与乱序

| 防线 | 手段 | 覆盖场景 |
|---|---|---|
| 第一道 | Kafka 按业务主键分区 | 同订单变更有序 |
| 第二道 | 水位线 + 允许迟到 30 秒 | 轻微乱序 |
| 第三道 | MoW 后写覆盖 + 源端补正 | 严重乱序、重放：重复批次被 label 幂等吞掉；乱序由源端 2 秒后补正，DWD 可能短暂倒退（Q10 计数），不用 `update_time` 比大小（08 E31） |
| 第四道 | 离线 T+1 补数 | 超出实时窗口的迟到数据 |

**四道防线是递进的，不是重复的。** 如果只答"我设了水位线"，说明没想清楚。

## 七、容错与恢复

| 场景 | 处理 |
|---|---|
| Flink 作业失败 | 从最近 checkpoint 恢复；Doris 侧靠 2PC 回滚未提交事务 |
| Kafka 积压 | 提高并行度（受分区数限制）或加分区；先看反压定位瓶颈 |
| Doris 写入失败 | connector 重试；失败超阈值触发告警，作业挂起而非丢弃 |
| 维表缺失（商品已下架） | 打宽时兜底为"未知商品"维度，不丢单 |
| 全链路重跑 | 实时从 savepoint 重放 Kafka；离线 `INSERT OVERWRITE` 分区重算 |

## 八、可观测性

| 指标 | 采集点 | 阈值 |
|---|---|---|
| 端到端延迟 | `event_time` 与 Doris 写入时间之差 | P99 < 5s |
| 反压 | Flink UI 的 backpressure 面板 | 持续 high 告警 |
| checkpoint 时长 | Flink metrics | > 60s 关注 |
| Doris 版本数 | `SHOW TABLET` / compaction 状态 | 出现 `-235` 告警 |
| 脏数据量 | `dwd_dirty_record` 行数 | 突增告警 |
| 对账差异率 | `ads_reconcile_diff` | > 0.1% 告警 |

**延迟的定义要写死：** 用事件时间到入库时间的差值，不是"作业处理耗时"。否则指标好看但没有意义。

延迟的采集方式：`scripts/latency_probe.sh` 在测量窗口内每 10 秒投一条 0.01 元测试单，记录"写入 MySQL → 在 `dwd_trade_order_detail` 可见"的差值，落 `dw.latency_probe`，看板读 P50/P99。窗口模式与副作用边界见 [08](./08-问题索引.md) D32 / E34。

## 九、已知薄弱点

1. **无高可用**：单机 WSL，FE/BE 各一个实例，没有副本；真实生产需要 3 FE + 多 BE。
2. **离线不回放 Kafka**：离线直接读 MySQL，无法重建"某个时刻的实时视图"，也无法用离线修复 Kafka 里的脏数据。
3. **维表当天延迟**：每日快照意味着当天新增的商品在实时链路里 join 不到，会落到"未知商品"兜底。生产环境应该改成实时 CDC 维表 + 广播。
4. **无数据血缘**：表之间的依赖靠文档维护，没有自动解析。
5. **告警不闭环**：只落表，没接飞书 / 邮件通知。
6. **单机资源有限**：WSL 分配 23 GB 内存（`free -g` 实测），要同时跑 Kafka、Doris、Flink、Hive、Spark，压测时需错峰，见第十节。
7. **批链路靠手动触发**：机器不是 7×24 在线，T+1 作业不配 cron，靠开机后手动运行 `nightly_t1`，断档用日期区间补跑。DS 仍是编排器，只是不当定时器。生产环境应交给常驻调度器，并配失败告警。

主动写薄弱点不是为了减分，而是为了让评审者知道**边界在哪**——被问到时能答出"生产该怎么改"。

## 十、单机启动顺序与资源预算

WSL：23 GB 内存 / 32 核。全部组件能同时跑，但要按依赖顺序起，并且显式限制堆：

| 顺序 | 组件 | 堆/内存 | 起完的检查 |
|---|---|---|---|
| 1 | MySQL | 系统默认 | `mysql -uroot -e 'select 1'` |
| 2 | HDFS（NameNode + DataNode） | 2 GB × 2（实测 `-Xmx2048m`） | `curl 127.0.0.1:9870` 返回 302 |
| 3 | Hive Metastore | 2 GB | `ss -lntp \| grep 9083` |
| 4 | Kafka（KRaft） | 1 GB | `kafka-topics.sh --list` |
| 5 | Doris FE / BE | FE 4 GB；BE 的 JVM 2 GB，`mem_limit` 需显式设 6~8 GB | `SHOW BACKENDS` 里 `isAlive=true` |
| 6 | Flink | JobManager + TaskManager，各 4 GB 以内 | 8081 能打开 |
| 7 | DolphinScheduler | 按官方默认 | 12345 能打开 |
| 8 | Grafana（按需） | 约 0.3 GB（Go 进程，无 JVM 堆） | `curl 127.0.0.1:3000/api/health` 返回 `ok` |

**当前实测**（2026-11-24）：MySQL + HDFS + Hive + Kafka + Doris 起完后 `free -g` 为 used 10 GB / available 13 GB，Flink 与 DS 尚未启动。也就是留给 Flink 和 DS 的余量约 13 GB。

**两条纪律：**

1. **Doris BE 的 `mem_limit` 必须显式配。** BE 默认按物理内存的 80% 申请，23 GB 的机器会直接吃掉 18 GB，Flink 一起就 OOM。
2. **压测时不同时跑离线。** `offline_t1` 的 Spark 全量重算和压测错开，DS 也不必常开——批任务跑完就能停。
