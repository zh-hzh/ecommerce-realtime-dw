## 二、为什么是 Lambda，不是 Kappa

| 维度 | Lambda（选它） | Kappa |
|---|---|---|
| 链路 | 实时 + 离线两条 | 只有流处理一条 |
| 准确性 | 离线做 T+1 精确结算 | 依赖事件回放重建 |
| 对账 | 天然有两个独立结果可比 | 自己和自己比，无法发现系统性偏差 |
| 成本 | 多维护一条离线链路 | 链路短 |

选 Lambda 的唯一决定性理由：**对账需要两个独立的计算结果**。Kappa 架构下只有一个结果，没法证明它对不对。而"我怎么保证实时数据可信"正是这个项目要回答的核心问题。

代价是离线链路要额外维护，但 Spark + Hive 你已有两个项目的基础，成本可控。

## 三、组件职责边界

| 组件 | 只负责 | 不负责 |
|---|---|---|
| MySQL | 产生权威交易数据 | 分析查询 |
| Flink CDC | 抓 binlog 写入 Kafka | 清洗、聚合 |
| Kafka | ODS 缓冲与解耦、保证分区内有序 | 长期存储（7 天） |
| Flink SQL | 清洗、打宽、聚合、写 Doris | 数据服务 |
| Doris | 存储与 OLAP 查询 | 数据加工 |
| Spark + Hive | T+1 精确重算 | 秒级查询 |
| DolphinScheduler | 调度维表快照、离线作业、对账、质量巡检 | 流作业的提交、重启与恢复 |

**一条原则：每一层只做一件事。** CDC 作业里不写清洗逻辑，聚合不在 Doris 里做，看板只查 ADS。

## 四、数据链路与作业划分

### 4.1 Kafka topic 设计

| topic | 分区 | Key | 保留 | 用途 |
|---|---|---|---|---|
| `ods_order` | 3 | `order_id` | 7 天 | 订单变更 |
| `ods_order_detail` | 3 | `order_id` | 7 天 | 订单明细（只追加） |
| `ods_payment` | 3 | `order_id` | 7 天 | 支付流水 |
| `ods_refund` | 3 | `order_id` | 7 天 | 退款流水 |
| `ods_traffic` | 6 | `user_id` | 7 天 | 埋点事件 |

**Key 一律用业务主键**：同一个 `order_id` 的多次变更必然落在同一分区、同一条消费流里，顺序不乱。这是解决乱序的第一道防线，比在 Flink 里靠 `update_time` 兜底更根本。

**为什么单独给明细一个 topic：** MySQL 有 7 张表，其中 `order_detail` 只在下单时插入一次、之后不变。它不参与订单状态机，但实时侧要算"商品粒度 GMV / TOP N 商品"就必须有它。放进 `ods_order` 会把两种 schema 混在一条流里，所以单开 `ods_order_detail`，同样用 `order_id` 做 key，保证同一订单的明细与主单落在同一分区。

分区数决定并行度上限：订单类 3 个分区 → Flink 并行度最多 3；流量 6 个 → 最多 6。

**为什么订单类只给 3 个分区：** 日常订单量是 20 单/分钟，3 个分区绰绰有余；压测只压埋点（2000 QPS，6 个分区），订单链路不是瓶颈。所以 3 并行度够用，不构成"压测压不上去"的问题。

**真要扩订单并行度，只能重建 topic：** 加分区会打乱 `key` 到分区的映射，同一 `order_id` 的历史数据仍留在旧分区、新数据去新分区，顺序保证失效。流程是"建新 topic → 作业双写 → 存量回放 → 切读新 topic → 删旧 topic"，需要短暂停写。这是 [05-数据源与造数](./05-数据源与造数.md) 里写"分区数不要事后改"的实际含义。

### 4.2 作业清单

| 编号 | 作业 | 输入 | 输出 | 并行度 | 类型 |
|---|---|---|---|---|---|
| J1 | `cdc2kafka` | MySQL binlog | Kafka 四个交易 topic（`ods_traffic` 由埋点生成器写） | 1 | 流 |
| J2 | `dwd_trade` | ods_order/payment/refund/detail + DIM | `dwd_trade_order_detail` | 3 | 流 |
| J3 | `dws_trade` | `dwd_trade_order_detail` + `ods_order_detail` + `dim_product` | `dws_trade_1min` / `_shop_1h` / `_product_1h` | 3 | 流 |
| J4 | `dwd_traffic` | `ods_traffic` | `dwd_traffic_detail` + `dwd_dirty_record` | 6 | 流 |
| J5 | `dws_traffic` | `dwd_traffic_detail` | `dws_traffic_1min` / `dws_user_1d` | 6 | 流 |
| J6 | `ads_refresh` | DWS 三层 | `ads_*` 三张 | 1 | 流 |
| O1 | `offline_t1` | MySQL | Hive DWD/DWS/ADS | — | Spark 批 |
| O2 | `reconcile` | Hive ADS + Doris ADS | `ads_reconcile_diff` | — | SQL |

**J2 是核心难点**：订单 / 支付 / 退款三条流要合并成"一行一单"的累积快照，再 Lookup Join 维表打宽。这里同时涉及多流合并、维表关联、幂等更新三件事。最终没走 interval join：订单里程碑跨度最长 20 天，窗口留不住，且订单流单独触发时拿不到支付/退款字段；改成**三条流各写各的列，Doris 部分列更新合并**（见下方第三版）。

**J2 分三版落地（2026-11-25）**：首版只接 `ods_order` 单流写 `dwd_trade_order_detail`，目的是先打通 Kafka → Flink → Doris 并验证实时可见与幂等更新，脚本为 `flink/sql/j2_dwd_trade.sql` + `scripts/run_j2.sh`，冒烟 `scripts/smoke_j2.sh`（插入/更新/软删三步都在 Doris 查到，各约 10~12 秒，受 10s checkpoint 约束）。

**第二版（2026-11-25）：`dim_shop` Lookup Join 补齐省市。** `dw.dim_shop` 由 `scripts/load_dim_shop.sh` 从 MySQL `shop_info` 全量导 2000 行（mysql 导 TSV → curl Stream Load 到 FE），J2 SQL 里源表加 `proc_time AS PROCTIME()`，用 `LEFT JOIN dw.dim_shop FOR SYSTEM_TIME AS OF o.proc_time` 点查维表，`province`/`city` 不再是 NULL。lookup 缓存 5000 行 / 10 分钟，单行命中不会膨胀。冒烟脚本同步加了断言：测试单 `shop_id=1` 的省市必须与 MySQL 一致（实测 `广东 / 佛山`），插入约 4~6 秒可见，更新/软删约 12 秒可见。支付/退款字段仍是后续增量。

**第三版已落地（2026-11-25）：支付/退款并入 DWD。** 作业里三条流各写各的列，用 `EXECUTE STATEMENT SET` 提交为同一个作业：订单分支写订单字段 + 省市，支付分支写 `pay_id/pay_amount/pay_status/pay_time`（只取成功支付），退款分支写 `refund_amount/refund_time/refund_status`（只取成功退款）。Doris 侧 `partial_columns=true`，每个 sink 的 Flink DDL 只声明自己那几列，`sink.properties.columns` 只列这几列——**列没列进去就不动，列进去了但 JSON 缺 key 会被置 NULL**（实测见 08 E20）。三个 sink 各自独立的 label 前缀（`j2_order_v3` / `j2_pay_v3` / `j2_refund_v3`）。据此 DWD 表的 key 从 `(order_id, dt)` 改为 `order_id`、取消 `dt` 分区（D20）。冒烟覆盖"下单 → 支付 → 退款 → 软删"四段，每段都断言前一段的列没被冲掉，实测每段约 10~12 秒可见。

**J3 的商品粒度来自明细流，不是 DWD。** DWD 是订单粒度的累积快照，一个订单多件商品塞不进去。`dws_trade_product_1h` 直接消费 `ods_order_detail` 再 Lookup `dim_product` 取快照类目，按 `stat_hour + product_id` 累加支付金额与笔数，供实时 TOP N 商品和分品类 GMV 使用。

**连接器已就位**（2026-11-25 实测）：`flink/lib` 下有 `flink-sql-connector-mysql-cdc-3.7.0-1.20.jar` 和 `flink-doris-connector-1.20-25.1.0.jar`，J1 与写 Doris 的作业都不缺包。

**J1 必须用 `scan.startup.mode=latest-offset`。** 库里已有 90 万历史单、298 万明细，若用默认的 `initial` 会先做全量快照，开局就把近 500 万行灌进 4 个交易 topic。历史数据只给离线链路用，实时链路只处理 J1 启动之后的变更。

**O2 对账不重跑流作业。** 两条链路各出一个 T-1 全天结果，再逐指标比：

| 侧 | T-1 结果从哪来 | 说明 |
|---|---|---|
| 实时 | Doris 的 `dt=T-1` 分区 | ADS/DWS 是全天覆盖写，日终后分区里就是 T-1 全天值；若有水位线外的迟到，在该分区上用 DWD 跑一条 T-1 聚合 SQL 修正 |
| 离线 | Hive 的 `dt=T-1` 分区 | Spark 从 MySQL 重算 |

两边都是批查，互不影响，**实时链路不中断**。真正回放 Kafka 只用于故障恢复，不用于日常对账——重放会重复写入，还得再清一遍。

**离线抽数用 Spark JDBC 直读 MySQL**，不经过 Kafka 也不落 HDFS 中转：对账基准必须是权威源（决策 #4），而 Kafka 里有重复和迟到，不能当基准。[05-数据源与造数](./05-数据源与造数.md) 里的 90 万历史单是直接 `INSERT` 进 MySQL 的，Spark 按天读出来就是完整的一天。

**7 张表全部走离线快照，包括 `order_detail`。** 明细在实时侧另有 `ods_order_detail` topic，但那只是流内的商品维度来源；离线链路的 `ods_order_detail` 是 Spark JDBC 按 `dt` 全量抽的 Hive 表，和质量巡检 C02 的订单-明细勾稽对得上。两条路同源（都来自 MySQL），互不依赖——实时明细丢了不影响离线，离线没跑也不影响实时。

**首次启动顺序不能颠倒**：先建表灌维表（`scripts/init_doris.sh` + `scripts/load_dim_shop.sh <mysql_root_password>`），再启 J2。否则 Lookup Join 全命中不到维表，订单的省市为 NULL——不丢单，但首日的分省分析全废。

### 4.3 调度职责（DolphinScheduler）

**定位：只做批编排，不做流调度。** 下面四个节点不是四份独立调度，而是**一条工作流 `nightly_t1` 的四个串行步骤**——DS 在这里是编排器，不是定时器。

| 任务 | 内容 | 跑批顺序 | 上游依赖 |
|---|---|---|---|
| `dim_snapshot` | MySQL → Doris 三张维表快照 | ① | 无 |
| `offline_t1` | MySQL → Hive ODS/DWD/DWS/ADS | ② | `dim_snapshot` 完成 |
| `reconcile` | Hive ADS × Doris ADS → `ads_reconcile_diff` | ③ | `offline_t1` 完成 |
| `quality_check` | 5 类规则跑批 → 写脏数据表 / 出日报 | ④ | `reconcile` 完成 |
| `backfill` | 按日期区间重跑指定分区 | 手动，独立 | 无 |

**不用 cron 定时。** 这台机器是个人电脑，凌晨不在线，写死"每日 04:00"的对账永远不会被执行。所以四个步骤做成一条**手动触发**的工作流 `nightly_t1`：

| 事项 | 做法 |
|---|---|
| 触发 | 开机后打开 DS，手动运行一次 |
| 日期参数 | 默认 `dt = T-1`，对账确认的是"昨天那一整天" |
| 断档补跑 | 连续几天没开机，填 `start_dt` / `end_dt`，按日期逐个实例跑 |
| DS 自动补数 | 不依赖。DS 的补数是手动点的，机器没开时不会自己长出来 |

对账是否准确只取决于"取的是 T-1 分区"，与几点触发无关；真正要守的是"跑完就冻结当天结论，之后重跑以新结果为准"（见 [06-数据质量与对账](./06-数据质量与对账.md) 6.3）。

**依赖按"数据就绪"判断，不按 cron 硬等。** 每个下游任务启动前先探测上游产物是否可用（Hive 分区是否存在、Doris 表当日分区是否有数据），不可用则失败退出而不是继续跑。按时间死等会在上游延迟时读到空分区，产出脏数据。

**DS 不负责的三件事：**

| 不做 | 原因 |
|---|---|
| 提交或重启实时作业 | Flink 靠 checkpoint + `restart-strategy` 自愈，不需要外部拉起 |
| 分钟级及以下的调度 | DS 是批调度器，不适合流任务节奏 |
| 实时作业之间的编排 | 实时作业顺序由 Kafka topic 与消费关系天然决定 |

这一条要在设计说明里讲清楚：**调度器不是流计算的高可用方案。** 流作业的恢复依赖 checkpoint 与状态后端，不依赖每分钟探测。

**落地顺序：先脚本，后编排。** 这五个任务每一个都跨组件，先在命令行跑通再搬进 DS：

| 任务 | 先手工跑通的东西 | 搬进 DS 后只管 |
|---|---|---|
| `dim_snapshot` | 一条 JDBC 抽数 + Stream Load 的脚本 | 触发时间、失败重试 |
| `offline_t1` | 一个 `spark-submit`（JDBC 读 MySQL → 写 Hive 分区） | 依赖 `dim_snapshot` |
| `reconcile` | 两条 SQL（Doris 侧、Hive 侧）+ 一条写差异表的 SQL | 依赖 `offline_t1` |
| `quality_check` | 每条质量规则一条 SQL，结果 `INSERT` 质量表 | 依赖 `reconcile` |
| `backfill` | 带日期参数的同一套脚本 | 无 |

这样出问题时能绕过 DS 单独重跑某一步，排错半径小；DS 只是编排器，不承载业务逻辑。**当前 DS 已安装但未启动**，这五个任务都还没建。

> 易混点：DS 自带 Flink 任务类型，但那是"作业部署与生命周期管理"，属于平台能力，不是"流调度"。生产上常见，本项目不使用。

## 五、关键决策记录

| # | 决策 | 放弃的方案 | 理由 |
|---|---|---|---|
| 1 | CDC 用 Flink CDC 3.x | Canal / Maxwell | 不用额外部署组件；与 Flink 同栈；全量 + 增量一体 |
| 2 | CDC 先写 Kafka，再由 Flink SQL 读 | CDC 直写 Doris | 解耦；Kafka 可被多个下游消费；出问题能重放 |
| 3 | ODS 放 Kafka，不放 Doris | ODS 也落 Doris | Kafka 是天然的追加日志；Doris 存 ODS 只会放大 compaction 压力 |
| 4 | 离线以 MySQL 为基准 | 从 Kafka 落湖再算 | **对账基准必须是权威源**；Kafka 有丢失和重复，不能当基准 |
| 5 | Flink SQL 而非 DataStream | Java DataStream | 社区主流写法；迭代快；窗口与 join 表达力足够 |
| 6 | UV 用 Doris bitmap | Flink 状态去重 | 可跨维度精确上卷；状态不会无限膨胀 |
| 7 | 维表每日全量快照 | 实时 CDC 维表 | 维表变更低频；快照可回溯；实现简单 |
| 8 | DWS 用 Aggregate 模型 | Unique 模型 | 写入即聚合，查询快；DWS 不需要明细 |
| 9 | Kafka 用 KRaft（broker + controller 合一） | ZooKeeper 模式 | 3.x 起 KRaft 已生产可用；少一个组件、少一套选举逻辑；ZooKeeper 模式官方已宣布逐步移除 |
| 10 | 所有服务监听绑 `127.0.0.1` | 绑 `0.0.0.0` 或宿主网卡 | 宿主 WLAN 为 DHCP，绑网卡地址会随 IP 变化失效 |

## 六、一致性设计

### 6.1 端到端语义

| 环节 | 保证 | 手段 |
|---|---|---|
| Kafka → Flink | 精确一次 | checkpoint 时提交 offset |
| Flink → Doris | 精确一次 | Doris connector 两阶段提交（2PC） |
| 兜底 | 幂等 | 主键 + `update_time` 覆盖，重复写入结果不变 |

两层设计：**2PC 保证不重不漏，幂等保证即使重了也不出错。** 被问到"怎么保证数据不重"时，要能同时讲出这两层。

### 6.2 checkpoint 配置

```yaml
execution.checkpointing.interval: 60s
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.timeout: 10min
state.backend.type: rocksdb
execution.checkpointing.min-pause: 30s
```

选 RocksDB 而不是内存：`dws_user_1d` 的 UV 集合和 interval join 的缓冲都在状态里，内存撑不住压测量级。

### 6.3 迟到与乱序

| 防线 | 手段 | 覆盖场景 |
|---|---|---|
| 第一道 | Kafka 按业务主键分区 | 同订单变更有序 |
| 第二道 | 水位线 + 允许迟到 30 秒 | 轻微乱序 |
| 第三道 | `update_time` 幂等覆盖 | 严重乱序、重放 |
| 第四道 | 离线 T+1 补数 | 超出实时窗口的迟到数据 |

**四道防线是递进的，不是重复的。** 如果只答"我设了水位线"，说明没想清楚。

## 七、容错与恢复

| 场景 | 处理 |
|---|---|
| Flink 作业失败 | 从最近 checkpoint 恢复；Doris 侧靠 2PC 回滚未提交事务 |
| Kafka 积压 | 提高并行度（受分区数限制）或加分区；先看反压定位瓶颈 |
| Doris 写入失败 | connector 重试；失败超阈值触发告警，作业挂起而非丢弃 |
| 维表缺失（商品已下架） | 打宽时兜底为"未知商品"维度，不丢单 |
| 全链路重跑 | 实时从 savepoint 重放 Kafka；离线 `INSERT OVERWRITE` 分区重算 |

## 八、可观测性

| 指标 | 采集点 | 阈值 |
|---|---|---|
| 端到端延迟 | `event_time` 与 Doris 写入时间之差 | P99 < 5s |
| 反压 | Flink UI 的 backpressure 面板 | 持续 high 告警 |
| checkpoint 时长 | Flink metrics | > 60s 关注 |
| Doris 版本数 | `SHOW TABLET` / compaction 状态 | 出现 `-235` 告警 |
| 脏数据量 | `dwd_dirty_record` 行数 | 突增告警 |
| 对账差异率 | `ads_reconcile_diff` | > 0.1% 告警 |

**延迟的定义要写死：** 用事件时间到入库时间的差值，不是"作业处理耗时"。否则指标好看但没有意义。

## 九、已知薄弱点

1. **无高可用**：单机 WSL，FE/BE 各一个实例，没有副本；真实生产需要 3 FE + 多 BE。
2. **离线不回放 Kafka**：离线直接读 MySQL，无法重建"某个时刻的实时视图"，也无法用离线修复 Kafka 里的脏数据。
3. **维表当天延迟**：每日快照意味着当天新增的商品在实时链路里 join 不到，会落到"未知商品"兜底。生产环境应该改成实时 CDC 维表 + 广播。
4. **无数据血缘**：表之间的依赖靠文档维护，没有自动解析。
5. **告警不闭环**：只落表，没接飞书 / 邮件通知。
6. **单机资源有限**：WSL 分配 23 GB 内存（`free -g` 实测），要同时跑 Kafka、Doris、Flink、Hive、Spark，压测时需错峰，见第十节。
7. **批链路靠手动触发**：机器不是 7×24 在线，T+1 作业不配 cron，靠开机后手动运行 `nightly_t1`，断档用日期区间补跑。DS 仍是编排器，只是不当定时器。生产环境应交给常驻调度器，并配失败告警。

主动写薄弱点不是为了减分，而是为了让评审者知道**边界在哪**——被问到时能答出"生产该怎么改"。

## 十、单机启动顺序与资源预算

WSL：23 GB 内存 / 32 核。全部组件能同时跑，但要按依赖顺序起，并且显式限制堆：

| 顺序 | 组件 | 堆/内存 | 起完的检查 |
|---|---|---|---|
| 1 | MySQL | 系统默认 | `mysql -uroot -e 'select 1'` |
| 2 | HDFS（NameNode + DataNode） | 2 GB × 2（实测 `-Xmx2048m`） | `curl 127.0.0.1:9870` 返回 302 |
| 3 | Hive Metastore | 2 GB | `ss -lntp \| grep 9083` |
| 4 | Kafka（KRaft） | 1 GB | `kafka-topics.sh --list` |
| 5 | Doris FE / BE | FE 4 GB；BE 的 JVM 2 GB，`mem_limit` 需显式设 6~8 GB | `SHOW BACKENDS` 里 `isAlive=true` |
| 6 | Flink | JobManager + TaskManager，各 4 GB 以内 | 8081 能打开 |
| 7 | DolphinScheduler | 按官方默认 | 12345 能打开 |

**当前实测**（2026-11-24）：MySQL + HDFS + Hive + Kafka + Doris 起完后 `free -g` 为 used 10 GB / available 13 GB，Flink 与 DS 尚未启动。也就是留给 Flink 和 DS 的余量约 13 GB。

**两条纪律：**

1. **Doris BE 的 `mem_limit` 必须显式配。** BE 默认按物理内存的 80% 申请，23 GB 的机器会直接吃掉 18 GB，Flink 一起就 OOM。
2. **压测时不同时跑离线。** `offline_t1` 的 Spark 全量重算和压测错开，DS 也不必常开——批任务跑完就能停。
