# 数据质量与对账

> 输入是 [02-指标体系](./02-指标体系.md) 的对账范围、[03-数据模型](./03-数据模型.md) 的两张质量表、[04-架构设计](./04-架构设计.md) 的作业划分、[05-数据源与造数](./05-数据源与造数.md) 的五类异常注入。
> 本文回答两个问题：**坏数据怎么拦住并留下证据**，**实时和离线差多少、差在哪**。截至 2026-11-25，流内 Q04 / Q05 / Q08 已随 J4 落地，其余规则与对账仍是设计。

## 一、两条质量防线

```
                ┌──────────────────────────────┐
MySQL / 埋点 ──>│ 流内校验（Flink，秒级）        │──拦截──> dwd_dirty_record
                │ 完整性 / 合法性 / 唯一性 / 及时性│
                └──────────────┬───────────────┘
                               │ 放行
                               ▼
                        DWD → DWS → ADS（Doris）
                               │
                ┌──────────────┴───────────────┐
                ▼ T+1 巡检                      ▼ T+1 对账
        ┌──────────────────┐            ┌──────────────────┐
        │ 批巡检（5 类规则） │            │ 对账（6 个指标）  │
        │ 跨表勾稽 / 分区完整│            │ Doris × Hive     │
        └────────┬─────────┘            └────────┬─────────┘
                 │                               │
                 └──────────> 质量结论 <──────────┘
                                  │
                                  ▼
                      差异明细 / 告警（人工处理）
```

| 防线 | 执行位置 | 时机 | 能发现什么 | 发现不了什么 |
|---|---|---|---|---|
| 流内校验 | J2 / J4 的 Flink SQL | 每条记录 | 单条记录自身的问题 | 跨表、跨天、系统性偏差 |
| 批巡检 | DS `quality_check` | 跑批第 4 步（手动触发） | 跨表勾稽、分区完整性、脏数据率 | 实时性要求高的问题 |
| 对账 | DS `reconcile` | 跑批第 3 步（手动触发） | 两条链路的系统性差异 | 单条记录的错（要靠明细定位） |

**流内校验不能替代对账。** 单条记录都合法，聚合结果仍可能错——重复、迟到、漏数都是"每条都合法"的错误。反过来，对账也不能替代流内校验：对账只知道总量差，不知道是哪条坏了。

## 二、五类规则与处置策略

规则按五个质量维度分组，和 05 的五类异常一一对应：

| 维度 | 定义 | 对应注入异常 |
|---|---|---|
| 完整性 | 该有的没有（维表缺失、必填为空） | 维表缺失 |
| 合法性 | 值不在允许范围（金额、枚举、时间） | 金额异常 |
| 一致性 | 同一条业务事实的多个副本对不上 | 金额异常、状态乱序 |
| 唯一性 | 同一事件被记了多次 | 埋点重复 |
| 及时性 | 数据到得太晚或顺序颠倒 | 支付迟到、状态乱序 |

**处置只分三种，不要混：**

| 处置 | 含义 | 是否写 `dwd_dirty_record` | 适用 |
|---|---|---|---|
| **拦截** | 不进 DWD 主表，只写脏数据表 | 是 | 值本身坏了，进主表会污染指标 |
| **兜底** | 进主表，但用默认值补维度 | 是 | 数据可用，只是缺描述信息 |
| **计数** | 正常处理（去重 / 幂等覆盖），只累加指标 | 否 | 系统能自动纠正的错误 |

**为什么重复和乱序不写脏表：** 它们有确定性的自动处理方式（主键去重、`update_time` 幂等覆盖），写进脏表只会让"脏数据"失去含义——脏表应该只放需要人判断的东西。这两类问题靠计数指标 + 阈值告警暴露。

## 三、流内规则（Flink，秒级）

| 编号 | 维度 | 规则 | 判定 | 处置 | 扫到哪张表 |
|---|---|---|---|---|---|
| Q01 | 合法性 | 订单金额非正 | `order_amount <= 0` | 拦截 | `ods_order` |
| Q02 | 合法性 | 支付金额非正 | `pay_amount <= 0` | 拦截 | `ods_payment` |
| Q03 | 合法性 | 退款金额非正或超额 | `refund_amount <= 0` 或 `> pay_amount + 0.01` | 拦截 | `ods_refund` |
| Q04 | 合法性 | 事件时间越界 | `event_time > now + 5min` 或 `< now - 30d` | 拦截 | `ods_traffic` |
| Q05 | 合法性 | 枚举非法 | `order_status` 不在 100/200/300/400/500/600，或 `event_type` 不在三种 | 拦截 | 全部 |
| Q06 | 完整性 | 维表未命中 | Lookup Join 返回 NULL | 兜底，维度填"未知商品/未知店铺" | DWD 打宽 |
| Q07 | 完整性 | 订单无明细 | 支付成功但 `order_detail` 无对应行 | 计数（P2） | DWD 打宽 |
| Q08 | 唯一性 | 埋点重复 | `event_id` 重复 | 计数（主键去重，不落脏表） | `ods_traffic` |
| Q09 | 及时性 | 支付迟到 | `event_time < watermark - 30s` | 计数（放行，幂等覆盖） | `ods_payment` |
| Q10 | 一致性 | 状态倒退 | 新记录 `update_time` 早于主表已有值 | 计数（丢弃该条更新） | DWD |
| Q11 | 一致性 | 已支付但无支付时间 | `order_status >= 200` 且 `pay_time IS NULL` | 计数（P2） | DWD |
| Q12 | 及时性 | 端到端延迟超阈 | 入库时间 − `event_time` > 5s | 计数（Flink metric 打点，P1） | 写 Doris 时 |

**Q01~Q05 拦截后不写 DWD**：这些值会直接算进 GMV、退款率，进主表就是污染。原样留在 `dwd_dirty_record`，人工确认后可修正并重放。

**Q06 兜底而不拦截**：商品下架后仍可能有在途订单，拦掉会导致对账少单。维度补"未知商品"（`product_id = -1` 的默认行），金额和笔数照常统计——这正是 [04-架构设计](./04-架构设计.md) 第七节的那条容错。

**Q08 / Q09 / Q10 只计数**：这三类如果写脏表，会占满大部分行数，把真正需要看的"拦截型"脏数据淹没。

**落地进度（2026-11-25，J4）：** Q04（`event_time` 超出 `[now-30d, now+5min]`）与 Q05 的埋点部分（`event_type` 不在三种、`event_id`/`user_id` 为空）已在 `flink/sql/j4_dwd_traffic.sql` 实现，落 `dw.dwd_dirty_record`，字段为 `dt, rule_id, source_table, biz_key, reason, raw_data, dirty_time`；`dt` 取拦截当天。Q08 的主键去重由 `dwd_traffic_detail` 的 `UNIQUE KEY(event_id, dt)` + merge-on-write 实现，重复计数指标尚未打点。Q01~Q03 的金额拦截、Q06 维表兜底、Q09~Q12 的计数指标仍未实现。

## 四、批巡检规则（DS，跑批内第 4 步）

五类规则用 SQL 跑，**不新建汇总表**——`dwd_dirty_record` 按 `rule_id` + `dt` 聚合就能出日报。执行位置按数据在哪分：C01 / C03 / C05 在 Doris；C02 依赖订单明细表，在 Hive 侧跑（离线 ODS 有全部 7 张 MySQL 表）；C04 两边都查。结果统一写回 Doris 的 `dwd_dirty_record`。

| 编号 | 维度 | 检查 | 判定 | 阈值 |
|---|---|---|---|---|
| C01 | 唯一性 | 主键重复 | `order_id` / `pay_id` / `refund_id` / `event_id` 在 DWD 有重复 | 0 条 |
| C02 | 一致性 | 订单-明细金额勾稽 | `ABS(SUM(order_detail.amount) - order_info.order_amount) > 0.01` | 0 条 |
| C03 | 一致性 | 支付金额与订单金额不等 | 全额支付场景下 `ABS(pay_amount - order_amount) > 0.01` | 0 条 |
| C04 | 完整性 | 分区完整性 | Doris 与 Hive 的 `dt = T-1` 分区存在且行数 > 0 | 缺一个即 FAIL |
| C05 | 完整性 | 脏数据率 | `dwd_dirty_record` 当日行数 ÷ DWD 当日行数 | < 1%（P1 告警） |

C01 是"防重复漏网"的最后一道：流内已经按主键去重，如果这里还能查到重复，说明 DWD 的 Unique Key 配置有问题（比如漏配 MoW），属于严重故障。

C04 必须先跑：分区不完整时后面的勾稽和对账都没有意义，直接 FAIL 并阻断下游。

样例（C02，Hive 侧跑，结果写回 Doris）：

```sql
INSERT INTO dwd_dirty_record (dt, rule_id, source_table, biz_key, reason, raw_data, dirty_time)
SELECT
  '${dt}', 'C02', 'dwd_trade_order_detail',
  CAST(o.order_id AS STRING),
  '订单金额与明细合计不符',
  CONCAT('order_amount=', o.order_amount, ', detail_sum=', d.amt),
  NOW()
FROM dwd_trade_order_detail o
JOIN (
  SELECT order_id, SUM(amount) AS amt
  FROM ods_order_detail WHERE dt = '${dt}' GROUP BY order_id
) d ON o.order_id = d.order_id
WHERE o.dt = '${dt}' AND ABS(o.order_amount - d.amt) > 0.01;
```

`ods_order_detail` 是离线 ODS 里的明细表（对应 MySQL 的 `order_detail`），不在 [03-数据模型](./03-数据模型.md) 的 17 张 Doris 表里。实时侧另有一个同名的 Kafka topic，只供 J3 算商品粒度，和这条批巡检无关。

**跨引擎这段谁执行：** DS 的 `quality_check` 是 Shell 节点，调 `spark-submit` 提交一个 PySpark 脚本——Spark 读 Hive 的 `dwd_trade_order_detail` 与 `ods_order_detail`，`filter` 出不符的行，再用 Doris Spark Connector（`spark-doris-connector`）或 JDBC 批量 `INSERT` 进 `dwd_dirty_record`。选 JDBC 也能跑，因为写入量是"脏数据行数"，通常几十行，不需要追求吞吐。Hive SQL 本身没有跨库写能力，所以这一步必须有 Spark（或 Flink 批）做桥梁，不能只写一段 Hive SQL。

注意 `dwd_dirty_record` 的 `dirty_id` 由作业生成（时间戳 + 序号），**不依赖数据库自增**——Doris 没有自增列，03 表清单里的"自增"只是编号语义。

## 五、脏数据旁路表

```sql
CREATE TABLE dwd_dirty_record (
  dirty_id    BIGINT       NOT NULL COMMENT '作业生成：毫秒时间戳*1000+序号',
  rule_id     VARCHAR(8)   NOT NULL COMMENT 'Q01~Q12 / C01~C05',
  rule_dim    VARCHAR(8)   NOT NULL COMMENT '完整性/合法性/一致性/唯一性/及时性',
  table_name  VARCHAR(64)  NOT NULL COMMENT '来源表',
  record_key  VARCHAR(64)  NOT NULL COMMENT '业务主键，定位用',
  raw_value   VARCHAR(2048) NOT NULL COMMENT '原始行 JSON，回放依据',
  fail_reason VARCHAR(256) NOT NULL COMMENT '不通过原因',
  action      VARCHAR(8)   NOT NULL COMMENT 'REJECT/FALLBACK/REPORT',
  event_time  DATETIME(3)  NULL COMMENT '事件时间，NULL 表示源端没有',
  dt          DATE         NOT NULL COMMENT '入库日期',
  create_time DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
) ENGINE=OLAP
DUPLICATE KEY(dirty_id)
PARTITION BY RANGE(dt) ()
DISTRIBUTED BY HASH(dirty_id) BUCKETS 4
PROPERTIES ("dynamic_partition.enable" = "true", "dynamic_partition.time_unit" = "DAY",
            "dynamic_partition.start" = "-90", "dynamic_partition.end" = "3",
            "dynamic_partition.prefix" = "p", "dynamic_partition.buckets" = "4");
```

五个字段的设计意图：

| 字段 | 为什么要有 |
|---|---|
| `rule_id` | 一条规则一条，日报直接 `GROUP BY rule_id`，也是回刷时的定位条件 |
| `record_key` | 没有它就只能全表扫 JSON；有主键才能"这条脏数据对应哪一单" |
| `raw_value` | 存原始行 JSON（不展开成列）。展开会让脏表变成第二张宽表，字段一改就要动表结构 |
| `action` | 区分"拦了"和"只是标记"，重放时只处理 `REJECT` |
| `dt` | 按入库日分区，与现有生命周期一致（90 天） |

**不保留完整链路信息**（offset、trace_id）：排查时用 `record_key` 回查 ODS 即可，脏表不是日志系统。

## 六、对账：六个指标

### 6.1 口径表

| 指标 | 实时侧来源（Doris） | 离线侧来源（Hive） | 类型 | 阈值 |
|---|---|---|---|---|
| 支付 GMV | `dws_trade_1min`，`dt = pay_date`，`SUM(pay_amt)` | 同口径 ADS | 金额 | < 0.1% |
| 支付笔数 | `dwd_trade_order_detail`，`COUNT(DISTINCT pay_id)` | 同口径 ADS | 笔数 | 0 |
| 退款金额 | `dwd_trade_order_detail.refund_amount`，**按 `create_time` 归日** | 同口径 ADS | 金额 | < 0.1% |
| 下单笔数 | `dwd_trade_order_detail`，`COUNT(DISTINCT order_id)`，按 `create_time` | 同口径 ADS | 笔数 | 0 |
| 支付用户数 | `dwd_trade_order_detail`，`pay_time` 非空且 `is_deleted = 0`，`COUNT(DISTINCT user_id)` | 同口径 ADS | 人数 | < 0.1% |
| 当日 UV | `dws_user_1d` 的 bitmap，`bitmap_union_count(uv)` | 同口径 ADS | 人数 | < 0.1% |

**退款金额实时侧为什么不用 `dws_trade_1min.refund_amt`：** DWS 里存的是"退款发生时间"口径，对账要的是"原订单时间"口径（见 [03-数据模型](./03-数据模型.md) 5.1）。两个口径不是一回事，直接比会把"往期订单本期退款"全部记成差异。这也是对账必须能从 DWD 重算、不能只查 ADS 的原因。

**ADS 侧取数前先刷新。** 三张 ADS 由 J6 定时刷新（默认 60 秒一次，`bash scripts/run_j6.sh`）；对账跑 T-1 时先执行 `bash scripts/run_j6.sh --dt <T-1>`，避免拿半天前的 ADS 去比全天的离线结果。

### 6.2 差异率与判定

```
diff_value = realtime_value - offline_value
diff_rate  = |diff_value| / offline_value        （offline_value = 0 时见下）
```

| 情况 | 判定 |
|---|---|
| 实时 = 离线 | PASS |
| 离线 = 0，实时 = 0 | PASS（分母 0 但两边都空） |
| 离线 = 0，实时 ≠ 0 | FAIL，`diff_rate` 置 NULL，`diff_value` 照记 |
| 金额类且 `diff_rate < 0.1%` | PASS（精度抖动范围内） |
| 金额类且 `diff_rate >= 0.1%` | FAIL |
| 笔数/人数类有任意差异 | FAIL（0 容忍） |

笔数类 0 容忍的理由：笔数差 1 就说明有单漏了或重了，这不是精度问题。金额类留 0.1% 是因为 `DECIMAL` 与 `DOUBLE` 求和顺序不同会产生分位误差。

### 6.3 对账时点与冻结

- `reconcile` 由 `nightly_t1` **手动触发**，不是凌晨定时（[04-架构设计](./04-架构设计.md) 4.3）。触发时 `dt = T-1`，那一天已经结束，Doris 的 `dt=T-1` 分区就是全天覆盖写的结果。几点跑不影响数值，只影响什么时候能看到结论。
- 每次跑都记 `check_time`；同一 `stat_date` 重跑会覆盖（`ads_reconcile_diff` 主键 `stat_date + metric`），历史值不保留，差异轨迹看任务日志。
- **以跑批时刻冻结结论**：跑批之后到的水位线外数据仍会进 T-1 分区，但不会自动改写已出的结果；下次重跑覆盖，以最新一次为准。这也是个人电脑做不到"凌晨固定跑"的必然结果——结论的可信度靠可重跑保证，不靠跑得早。

## 七、差异表与差异定位

### 7.1 `ads_reconcile_diff`

```sql
CREATE TABLE ads_reconcile_diff (
  stat_date      DATE          NOT NULL COMMENT '对账日期 T-1',
  metric         VARCHAR(32)   NOT NULL COMMENT '指标英文名',
  realtime_value DECIMAL(18,2) NOT NULL,
  offline_value  DECIMAL(18,2) NOT NULL,
  diff_value     DECIMAL(18,2) NOT NULL,
  diff_rate      DOUBLE        NULL COMMENT '离线为 0 时置 NULL',
  threshold      VARCHAR(16)   NOT NULL COMMENT '0 或 0.1%',
  status         VARCHAR(8)    NOT NULL COMMENT 'PASS/FAIL',
  check_time     DATETIME(3)   NOT NULL
) ENGINE=OLAP
UNIQUE KEY(stat_date, metric)
DISTRIBUTED BY HASH(stat_date) BUCKETS 4;
```

`UNIQUE KEY` 覆盖写：同一日期同一指标只留最新一次结果，看板只需要"当前结论"。

### 7.2 差异明细：不落表，现查

差异表只回答"差多少"，"差在哪"用临时查询。**不建差异明细表**——差异明细是一次性的排查产物，落表只会多一张需要维护的表。

三类差异的定位方式（用 Spark 同时 JDBC 读 Doris 与 Hive，按主键 full join）：

| 类型 | 现象 | 定位 SQL 思路 |
|---|---|---|
| 实时多 | 实时有、离线无 | Doris DWD 主键 `LEFT ANTI JOIN` 离线主键集 |
| 实时少 | 离线有、实时无 | 反过来的 `LEFT ANTI JOIN`，优先查 CDC 位点与迟到计数 |
| 值不等 | 两边都有，金额/状态不同 | 按主键 join 后 `WHERE ABS(a.amt - b.amt) > 0.01` |

### 7.3 差异归因表（排除法）

| 现象 | 优先怀疑 | 怎么验证 |
|---|---|---|
| 实时少、差一笔或几笔 | 迟到未到（水位线外） | 查 Q09 计数、Kafka 该分区 lag |
| 实时多、差一笔或几笔 | 重复未去重 | 查 `pay_id` 重复（C01）、离线分区行数 |
| 差异率固定在同一量级（如 1%） | 过滤条件不一致（时区、`is_deleted`、状态枚举） | 对比两边 WHERE 条件 |
| 金额差几分钱 | `DECIMAL` / `DOUBLE` 求和精度 | 看 `diff_value` 分布，不应随数据量放大 |
| UV 差、其他指标正常 | bitmap 跨天未清零、埋点重复 | 查 00:00 边界与 Q08 重复率 |
| 全指标同时差 | 分区不完整或离线任务失败 | 查 C04、`offline_t1` 日志 |

## 八、阈值与告警

| 级别 | 触发条件 | 处置 |
|---|---|---|
| **P0** | 对账任一指标 FAIL；C04 分区缺失 | 当天必须定位；对外报数前先说明 |
| **P1** | 脏数据率 > 1%；单条规则日环比突增 3 倍；端到端 P99 > 5s | 当天排查，判断是规则失效还是数据变坏 |
| **P2** | Q07 / Q11 偶发；Q09 迟到率 > 1% | 记录，随日报看趋势 |

**告警当前不闭环**：只落表，不接飞书 / 邮件（[04-架构设计](./04-架构设计.md) 已知薄弱点 #5）。查法就是 SQL：

```sql
-- 当日需要处理的规则
SELECT rule_id, rule_dim, action, COUNT(*) AS cnt
FROM dwd_dirty_record
WHERE dt = CURRENT_DATE()
GROUP BY rule_id, rule_dim, action
ORDER BY cnt DESC;

-- 最近三天的对账结论
SELECT stat_date, metric, realtime_value, offline_value, diff_rate, status
FROM ads_reconcile_diff
WHERE stat_date >= DATE_SUB(CURRENT_DATE(), 3)
ORDER BY stat_date DESC, metric;
```

## 九、怎么证明规则真的有用

规则写出来不算完，要能对上 [05-数据源与造数](./05-数据源与造数.md) 注入的异常。对照表：

| 注入异常 | 注入比例 | 期望命中规则 | 观察点 | 允许误差 |
|---|---|---|---|---|
| 埋点重复 | 5% | Q08（计数） | 去重量 / 总入量 ≈ 5%，DWD 行数不翻倍 | ±0.5% |
| 支付迟到 | 1% | Q09（计数） | 迟到计数 / 支付总量 ≈ 1% | ±0.3% |
| 状态乱序 | 0.5% | Q10（计数） | 丢弃更新数 / 订单更新数 ≈ 0.5% | ±0.2% |
| 金额异常 | 0.2% | Q01 / Q02 / Q03（拦截） | 三张 dirty 表命中量 / 注入量 ≈ 100% | 允许 ±10% |
| 维表缺失 | 少量 | Q06（兜底） | 未知商品占比 > 0，且订单笔数不缺 | 无 |

**允许误差的原因**：注入是按概率独立抛的，样本小时比例会偏；金额异常可能同时触发 Q01 和 Q03（金额为负的退款），去重后命中量会略少。**如果命中量是 0，说明规则没生效，不是"注入没抛中"。**

金标准：对账结果。注入的异常最终都会体现在指标上——重复会让实时支付笔数偏多，迟到会让实时 GMV 偏少。规则和注入都做对了，对账差异应该能被逐项归因，而不是"大概差不多"。

## 十、验收标准

| 检查 | 期望 |
|---|---|
| 五类异常各注入一批 | 上表五个规则都有记录，量级符合 |
| 正常数据 | 脏数据率 < 0.1%（远低于 1% 的告警线） |
| 六个对账指标 | 连续 3 天 PASS；或 FAIL 的差异能按 7.3 归因到具体原因 |
| 差异定位 | 任取一天能拉出"实时多 / 实时少 / 值不等"的明细 |
| 重复与乱序 | 脏表里查不到这两类，但计数指标非 0 |
| 重跑 | `reconcile` 同一天跑两次结果一致 |

## 十一、已知取舍

1. **不引入质量平台 / 流式规则引擎。** 规则是 Flink SQL 里的 WHERE 分支加 Doris 里的 SQL，规则多了会难维护；生产应上独立规则引擎，本项目只证明"知道该测什么"。
2. **不自动修复。** 拦截型脏数据只落表，修正后靠 `backfill` 手动回刷；自动修需要判断业务语义，不敢做。
3. **告警不闭环。** 没有通知渠道，靠人查 SQL。
4. **对账只覆盖 6 个指标。** 不做字段级全量比对（那样更接近数据迁移校验，不是数仓对账）。
5. **结论以跑批时刻冻结。** 跑批之后到的数据不自动追改，靠重跑覆盖。个人电脑不具备 7×24 在线条件，所以整条链是手动触发的，不做"每天几点必出数"的承诺。
6. **脏表存 JSON 原文，不展开列。** 牺牲可查询性换稳定性；需要按字段过滤时回查 ODS。
