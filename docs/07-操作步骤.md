# 07-操作步骤

**是什么**：从零启动到出数、对账的完整操作手册。

**干什么**：把「先跑什么、后跑什么」写成 7 个阶段，每个阶段给出可直接复制的命令、预期输出、失败时看哪里。

**怎么用**：第一次搭建看阶段 0~1；日常启动看阶段 2~3；每天跑批看阶段 4~5；改完代码或出问题看阶段 6~7。

> 本文只写「怎么跑」。为什么这样设计看 04-架构设计，表结构和口径看 03-数据模型，指标定义看 02-指标体系，对账规则看 06-数据质量与对账。

## 阶段 4：离线 T+1 跑批

**目的**：从 MySQL 抽出某一天的数据，在 Hive 里算出 DWD/DWS/ADS。

**前置**：阶段 0.5 完成；MySQL 里这一天数据已定型。

```bash
export MYSQL_PASSWORD='MySQL口令'
bash scripts/run_offline_t1.sh --dt 2026-11-25
```

不传 `--dt` 默认跑昨天。

**预期**：依次打印 `ods.order_info` / `ods.order_detail` / 维表 / `dwd_payment_detail` / `dwd_refund_detail` / `dwd_trade_order_detail` / `dws.trade_1d` 的分区行数，最后打印一行 ADS 结果（5 个指标）。

**三条铁律**：

1. **只跑已经结束的那一天**，并且跑完立刻对账（阶段 5），中间不要继续造数——实时侧还在增长，对账会永远对不上。
2. **可重复跑**：每个 `dt` 分区 `INSERT OVERWRITE`，重跑会覆盖，不会重复累加。
3. **按事件日切片**：支付按 `pay_time`、退款按 `refund_time` 落到当天分区。某天的退款如果发生在次日，不会出现在前一天的离线分区里（D27）。所以离线只能对「实时链路启动日之后、且当天已完全结束」的日期对账。

**失败时**：最上面会报缺 `MYSQL_PASSWORD` 或缺 JDBC jar；Spark 报时区错，检查脚本是否带了 `-Duser.timezone=Asia/Shanghai`（脚本已内置，不要手工裸跑 `spark-submit`）。

## 阶段 5：对账

**目的**：把 Hive 的离线结果和 Doris 的实时结果按 5 个交易指标逐项比较，差异写回 Doris。

**前置**：阶段 4 刚跑完同一天；Doris 实时链路一直在跑。

```bash
bash scripts/run_reconcile.sh --dt 2026-11-25
```

**预期**：打印 5 行结果并写入 `dw.ads_reconcile_diff`：

```text
stat_date   metric        realtime      offline       diff   rate    status
2026-11-25  order_cnt     603           603           0      0       PASS
2026-11-25  pay_cnt       589           589           0      0       PASS
2026-11-25  pay_user_cnt  564           564           0      0       PASS
2026-11-25  pay_amt       1611590.98    1611590.98    0      0       PASS
2026-11-25  refund_amt    153930.96     153930.96     0      0       PASS
```

**判定规则**（详见 06-数据质量与对账 6.2）：

| 情况 | 结论 |
|---|---|
| 笔数 / 人数类，`diff_value != 0` | FAIL（阈值 0） |
| 金额类，`diff_rate < 0.1%` | PASS |
| `offline = 0` 且 `realtime = 0` | PASS |
| `offline = 0` 且 `realtime != 0` | FAIL，`diff_rate` 为 NULL |

`diff_value = realtime - offline`。

**可对账的日期**：`>= 2026-11-25`（实时链路启动日）。更早的日期实时侧没有数据，不具可比性。

**失败时**：

- 先确认离线是不是跑的是同一天，以及跑完之后有没有继续造数；
- 笔数对不上先查 DWD 当天行数，再查 `dwd_dirty_record`；
- 历史退款缺失是口径限制（D27），不是 bug。

## 阶段 5B：批巡检 C01~C05

**目的**：把 06 四节的 5 条批巡检规则跑一遍，违规行写进 `dw.dwd_dirty_record`，供日报和告警取用。

**前置**：阶段 4（离线）与阶段 5（对账）已跑完同一天；Doris 9030、Hive metastore 9083 在线。不需要 MySQL 口令。

```bash
bash scripts/run_quality_check.sh --dt 2026-11-25
```

**预期**（2026-11-25 实测）：

```text
C04 PASS 分区完整
C01 PASS
C02 FAIL 41 条（已落 dwd_dirty_record）
C03 FAIL 38 条（已落 dwd_dirty_record）
C05 PASS 脏数据率 0.1679%
=== 结论：FAIL（退出码 1，阻断下游） ===
```

**FAIL 不等于链路坏了**：这 41 笔是造数脚本按 `--bad-amount-rate` 注入的 `order_amount=0`（11-25 当天注入率 6.8%，其他日期 0.2%），明细与支付金额都正确（E35）。要判真伪，回 MySQL 看 `order_info.order_amount` 原值即可。想让当天巡检变绿，造数时传 `--bad-amount-rate 0`。

**判定与重跑**：任一规则命中即 `exit 1`；C04 不通过会先落证据再退出，后面的勾稽不跑。同一 `dt` 重跑会先删掉 C01~C05 旧结果再插，行数不变（实测连跑两次 C02 都是 41 条）。

## 阶段 7：排障

| 现象 | 先执行 | 说明 |
|---|---|---|
| 不知道作业死没死 | `bash scripts/check_flink.sh` | 看 8 个作业状态 |

### 8.3 端到端延迟：测量窗口模式

探针平时不跑。需要时开一个 10 分钟窗口，每 10 秒投一条测试单，共 60 个样本，测完自动停。

```bash
# 前提：J1（CDC→Kafka）、J2（Kafka→DWD）在跑；要页面板也跟着动就再把 J3 起来
MYSQL_PASSWORD='MySQL口令' bash scripts/latency_probe.sh
# 可选：--duration 600 --interval 10 --timeout 120
```

脚本做三件事：

1. 往 `trade.order_info` 插一条 0.01 元、`order_status=100`（待支付）的测试单，并配一条 `order_detail`；`user_id` / `shop_id` / `product_id` 都是 `999999`，订单号固定 `999999` 开头。
2. 后台每 3 秒查一次 `dw.dwd_trade_order_detail`，出现即记 `latency_ms`；超过 `--timeout` 记 `success=0`。
3. 结果写入 `dw.latency_probe`，结束时打印样本数 / 成功数 / 平均 / P50 / P99。

**P50 在 10 秒左右是正常的**：J2 的 Doris sink 开了 2PC，数据要等 checkpoint（10 秒）完成才提交，所以理论下限就是 checkpoint 间隔（`docs/08` E19）。

副作用边界（测试单会不会污染数据）见 `docs/08` E34，要点：不进支付口径、不进 TOP N、不进漏斗分子；只影响那 10 分钟的 `order_cnt` 和 `order_amt`。

### 8.4 排障速查

| 现象 | 先查 |
|---|---|
| 页面打不开 | `bash scripts/grafana_start.sh status`，再 `tail ~/apps/grafana/log/grafana.log` |
| 面板报连接错误 | Grafana → Connections → Data sources → Doris → Save & test |
| 曲线是空的 | J3 在不在跑；生成器在不在跑 |
| 漏斗/TOP N 是空的 | 那天 J6 刷过没有：`bash scripts/run_j6.sh --dt 2026-11-25` |
| 延迟全是 success=0 | J1/J2 没跑，或测试单被当成脏数据丢掉（查 `dw.dwd_dirty_record`） |

## 阶段 9：DolphinScheduler 编排 nightly_t1

**目的**：把"维表快照 → 离线 T+1 → 对账 → 批巡检"四步串成一条可手动触发的工作流，失败即阻断下游。

### 9.1 启动 DS（standalone，元数据在 MySQL）

```bash
# 一次性：把 DS 的元数据从 H2 内存库切到 MySQL（库已初始化，64 张表）
#   standalone-server/conf/application.yaml:
#   datasource 改成 com.mysql.cj.jdbc.Driver + jdbc:mysql://127.0.0.1:3306/dolphinscheduler
#   password 写 ${DS_DB_PASSWORD:}（不落盘），并加 spring.sql.init.mode: never
# 详见 docs/08 E36

MYSQL_PASSWORD='MySQL口令' bash scripts/ds_keepalive.sh   # 后台跑；Ctrl-C 即停
# 就绪后打开 http://127.0.0.1:12345/dolphinscheduler/ui/  admin / 167836
```

**WSL 限制同 Flink**：`wsl.exe` 会话结束会回收非 systemd 进程，所以 DS 也要靠 `ds_keepalive.sh` 占住会话。

### 9.2 建工作流（脚本化，可重复执行）

```bash
DS_ADMIN_PASSWORD='admin口令' python3 scripts/ds_build_nightly_t1.py
# 已经建过会跳过；要重建加 --recreate；建完立即跑一次加 --start
```

脚本做的事：登录 → 确保项目 `ecommerce-realtime-dw` 存在 → 建 4 个 SHELL 节点并串行连好 → 需要时上线（未上线的工作流不允许触发，见 E36）→ 触发一次。

| 节点 | 做什么 |
|---|---|
| `dim_snapshot` | `load_dim_shop.sh` + `load_dim_product.sh`，刷新 Doris 三张维表快照 |
| `offline_t1` | `run_offline_t1.sh --dt ${dt}`，MySQL → Hive 四层 |
| `reconcile` | `run_reconcile.sh --dt ${dt}`，Hive ADS × Doris → `ads_reconcile_diff` |
| `quality_check` | `run_quality_check.sh --dt ${dt}`，C01~C05 → `dwd_dirty_record` |

全局参数 `dt` 默认 `$[yyyy-MM-dd-1]`（T-1），手动触发，`failureStrategy=END` 失败即停。**不配 cron**：个人电脑凌晨不在线，定时器没有意义（04 4.3）。

### 9.3 实测（2026-11-26，实例 18）

```text
dim_snapshot   SUCCESS  16:41:48 → 16:41:48
offline_t1     SUCCESS  16:41:49 → 16:42:13
reconcile      SUCCESS  16:42:14 → 16:42:23
quality_check  FAILURE  16:42:23 → 16:42:36   ← 出口码 1，C02 41 条 / C03 38 条
```

前三个节点按预期绿；`quality_check` 红是**设计如此**——11-25 的数据里有造数注入的 `order_amount=0`（E35、D33），巡检命中就阻断，不豁免。想看全绿，造数时把 `--bad-amount-rate` 设 0。

**DS 节点拿不到环境变量**：任务是以 `sudo -u hzh -i` 的登录 shell 执行的，`-i` 会重置环境。所以 MySQL 口令放在 `~/.ds/mysql_password`（`chmod 600`，只有 hzh 可读），登录脚本里 `export MYSQL_PASSWORD` 加载。不进仓库、不进工作流 JSON（E36）。

## 阶段 10：告警巡检

**目的**：一条命令回答"现在链路还正常吗"，有 FAIL 返回退出码 1，可当 DS 告警节点。

```bash
bash scripts/run_alert_check.sh
```

**实测（2026-11-26）**：

```text
[OK  ] flink_jobs   6 个作业全部 RUNNING
[OK  ] checkpoint   6 个作业本次提交以来 0 失败
[OK  ] kafka_lag    j4_traffic_valid=0, j4_traffic_dirty=0（阈值 100000）
[OK  ] dirty_rate   2026-11-26 脏 7520 / 总 3779461 = 0.1990%（阈值 1.00%）
[OK  ] reconcile    2026-11-25 五个指标全部 PASS
------------------------------------------------------------
结论：5 OK / 0 WARN / 0 FAIL
```

**阈值可调**：`ALERT_LAG_MAX`（默认 10 万）、`ALERT_DIRTY_RATE_MAX`（默认 0.01）、`ALERT_LAG_GROUPS`（默认 j4 两个消费组）。lag 超阈只 WARN —— 正常运行时 lag 随 10 秒 checkpoint 锯齿波动，2000 QPS 压测峰值约 2.1 万。

**为什么不是全 FAIL 口径**：dirty_rate 与 reconcile 直接对齐 06 的 P0/P1 线；flink_jobs / checkpoint 是"链路死了"级别；lag 是"可能跟不上"，所以降一级。
