# 指标体系

> 本文先于表结构存在，是刻意的：**指标决定模型**。表结构从这里的口径倒推，而不是先建表再想指标。

## 一、指标分层定义

| 层级 | 定义 | 本项目的例子 |
|---|---|---|
| **原子指标** | 不可再拆的业务度量，只来源于一个业务过程 | 支付金额、下单笔数、浏览量 |
| **派生指标** | 原子指标 + 修饰词（时间周期 / 维度限定） | 当日支付金额、分钟级浏览量、分省下单笔数 |
| **复合指标** | 由两个及以上派生指标做四则运算得到 | 支付转化率、客单价、退款率、复购率 |

判断标准：能直接 `SUM` / `COUNT` 出来的是原子；需要加时间窗或维度过滤的是派生；需要除法的才是复合。

## 二、命名规范

```
{业务域}_{业务过程}_{度量}_{周期}
```

| 段 | 取值 |
|---|---|
| 业务域 | `trade`（交易）、`traffic`（流量） |
| 业务过程 | `order`、`pay`、`refund`、`cart`、`view` |
| 度量 | `amt`（金额）、`cnt`（笔数/次数）、`uv`（去重人数） |
| 周期 | `1min`、`1h`、`1d` |

例：`trade_pay_amt_1min`（分钟级支付金额）、`traffic_uv_1d`（当日访客数）。

**复合指标不加周期后缀**，如 `trade_pay_rate`，因为它的周期由两个分子分母共同决定。

## 三、维度定义

| 维度 | 字段 | 取值 | 来源 |
|---|---|---|---|
| 时间 | `stat_minute` / `stat_hour` / `stat_date` | 按事件时间切分 | 事件时间 |
| 商品 | `product_id` / `category_id` / `brand` | 一级类目 + 品牌 | `dim_product` |
| 店铺 | `shop_id` / `shop_type` / `province` | 旗舰店 / 专卖店 / 专营店 | `dim_shop` |
| 用户 | `user_id` / `gender` / `age_range` / `city` | 性别、年龄段、城市 | `dim_user` |
| 渠道 | `pay_channel` | alipay / wechat / card | `payment_info` |

时间维度一律按**事件时间**（`create_time` / `pay_time` / `refund_time`），不按入库时间。这是实时与离线能对上的前提。

## 四、原子指标

| 指标 | 英文名 | 定义 | 来源 |
|---|---|---|---|
| 下单金额 | `order_amt` | `SUM(order_amount)`，按下单时间 | `order_info` |
| 下单笔数 | `order_cnt` | `COUNT(DISTINCT order_id)` | `order_info` |
| 支付金额 | `pay_amt` | `SUM(pay_amount)`，`pay_status = 成功` | `payment_info` |
| 支付笔数 | `pay_cnt` | `COUNT(DISTINCT pay_id)` | `payment_info` |
| 退款金额 | `refund_amt` | `SUM(refund_amount)`，`refund_status = 成功` | `refund_info` |
| 退款笔数 | `refund_cnt` | `COUNT(DISTINCT refund_id)` | `refund_info` |
| 浏览量 | `pv` | 去重后的 `COUNT(1)`，`event_type = page_view`（实现用 `COUNT(DISTINCT event_id)`，与 DWD 去重同口径，见 03 5.4 / 06 Q08） | `ods_traffic` |
| 访客数 | `uv` | `COUNT(DISTINCT user_id)`，`event_type = page_view`；实时侧落 `BITMAP`（03 八节） | `ods_traffic` |
| 加购次数 | `cart_cnt` | 去重后的 `COUNT(1)`，`event_type = add_cart`（实现同上） | `ods_traffic` |

## 五、派生指标

| 指标 | 英文名 | 口径 | 粒度 | 链路 |
|---|---|---|---|---|
| 分钟级支付金额 | `trade_pay_amt_1min` | 支付成功金额，按 `pay_time` 落分钟 | 分钟 | 实时 |
| 小时级支付金额 | `trade_pay_amt_1h` | 同上，落小时 | 小时 | 实时 |
| 当日支付金额 | `trade_pay_amt_1d` | 同上，自然日 | 日 | 实时 + 离线 |
| 当日净金额 | `trade_net_amt_1d` | `trade_pay_amt_1d − trade_refund_amt_1d`，同一天 | 日 | 实时 + 离线 |
| 当日支付笔数 | `trade_pay_cnt_1d` | 按 `pay_id` 去重 | 日 | 实时 + 离线 |
| 当日下单笔数 | `trade_order_cnt_1d` | 按 `order_id` 去重 | 日 | 实时 + 离线 |
| 当日退款金额 | `trade_refund_amt_1d` | 按退款发生时间归因 | 日 | 实时 + 离线 |
| 当日支付用户数 | `trade_pay_user_cnt_1d` | 按 `user_id` 去重 | 日 | 实时 + 离线 |
| 分钟级浏览量 | `traffic_pv_1min` | 按事件时间落分钟 | 分钟 | 实时 |
| 当日访客数 | `traffic_uv_1d` | 全天 `user_id` 去重 | 日 | 实时 + 离线 |
| 分省支付金额 | `trade_pay_amt_1d` @ province | 支付金额按店铺省份切分 | 日 | 实时 + 离线 |
| 分品类支付金额 | `trade_pay_amt_1d` @ category | 支付金额按一级类目切分 | 日 | 实时 + 离线 |

## 六、复合指标与口径详解

| 指标 | 公式 | 关键约束 |
|---|---|---|
| 支付转化率 | `trade_pay_cnt_1d ÷ trade_order_cnt_1d` | 分子分母必须同一时间窗、同一批订单 |
| 客单价 | `trade_pay_amt_1d ÷ trade_pay_user_cnt_1d` | **分母是支付用户数，不是订单数** |
| 退款率 | `trade_refund_amt_1d ÷ trade_pay_amt_1d` | 必须注明归因口径（见下） |
| 复购率 | 30 天内购买 ≥2 次的用户数 ÷ 30 天内购买用户数 | 窗口固定 30 天，不是自然日 |
| 加购转化率 | `trade_order_cnt_1d ÷ cart_cnt_1d` | 分子分母可能跨天，需注明 |

### 6.1 三个 GMV 口径

| 口径 | 定义 | 用途 |
|---|---|---|
| 下单 GMV | 下单金额合计 | 反映购买意愿，通常大于支付 GMV |
| **支付 GMV** | 支付成功金额合计 | **本项目的"GMV"默认指这个** |
| 净 GMV | 支付 GMV − 退款金额 | 财务口径，反映实际收入 |

**规则：任何提到 GMV 的地方必须写清是哪一种。** 对外表述统一用"支付 GMV"并带说明。

### 6.2 退款归因的两种方式

| 方式 | 说明 | 用在哪 |
|---|---|---|
| 按退款发生时间 | 退款算在退款当天 | 实时监控（能反映当天真实退款压力） |
| 按原订单时间 | 退款回溯到原下单日 | 离线结算（保证单日 GMV 最终准确） |

**本项目实时链路用前者，离线对账用后者。** 两者的差额必须能被解释（通常是"往期订单在本期退款"），这正好是可以展开讲的点。表结构上的落法见 [03-数据模型](./03-数据模型.md) 5.1：只存一份退款事实，实时口径按 `refund_time` 聚合，对账口径在 DWD 上按 `create_time` 重算。

### 6.3 UV 去重的三种错误

1. **分钟 UV 相加**：去重值不可加，`SUM(分钟UV) ≠ 日 UV`。
2. **窗口内累加**：实时当日 UV 是 `00:00 至今` 的去重累计，不是"上一分钟 UV + 当前分钟新增"。
3. **跨天边界**：离线按自然日去重，实时也必须在 `00:00` 清零，否则对不上。

实现方式：Doris 用 `bitmap` / `bitmap_union`，或 Flink 侧维护 `user_id` 集合状态。选型在数据模型文档里定。

## 七、实时与离线对账范围

| 对账指标 | 实时口径 | 离线口径 | 阈值 |
|---|---|---|---|
| 支付 GMV | T-1 全天重算 | T-1 分区 | < 0.1% |
| 支付笔数 | T-1 全天重算 | T-1 分区 | 0 笔差异 |
| 退款金额 | T-1 全天重算 | T-1 分区 | < 0.1% |
| 下单笔数 | T-1 全天重算 | T-1 分区 | 0 笔差异 |
| 支付用户数 | T-1 全天重算 | T-1 分区 | < 0.1% |
| 当日 UV | T-1 全天重算 | T-1 分区 | < 0.1% |

**对账方法：** 实时链路在 T+1 用同一批数据重算 T-1 全天结果（不是拿"当前累计"去比），与离线分区逐指标比对，差异率 = `|实时 − 离线| ÷ 离线`。超阈值时按主键拉出差异明细。

重算不重跑流作业：实时侧取 Doris 的 `dt=T-1` 分区（全天覆盖写的结果），必要时的修正在 Doris 内用 DWD 跑 T-1 聚合 SQL；离线侧取 Hive 的 `dt=T-1` 分区。实现细节见 [04-架构设计](./04-架构设计.md) 4.2。

笔数类指标用 0 容忍，金额类用 0.1%，因为金额可能有小数精度差异。

## 八、口径陷阱（高频）

| 陷阱 | 错误做法 | 正确做法 |
|---|---|---|
| GMV 混淆 | 把下单金额叫 GMV | 明确是支付 GMV |
| 客单价分母 | 除以订单数 | 除以支付用户数 |
| 退款率归因 | 不说明按哪个时间 | 明确按退款时间还是原订单时间 |
| UV 累加 | 分钟 UV 求和 | 全天 `user_id` 去重 |
| 实时比离线 | 拿"当前累计"比"离线全天" | 实时也重算 T-1 全天 |
| 重复支付回调 | 直接 `SUM` | 按 `pay_id` 去重，`update_time` 取最新 |
| 状态乱序 | 收到就更新 | 按 `update_time` 幂等覆盖 |
| 时区 | 混用 UTC 与本地时间 | 事件时间统一 epoch，展示用 Asia/Shanghai |
